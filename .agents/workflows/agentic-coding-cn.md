# Agentic 编码工作流

**使用时机**：在中/大规模任务（3个及以上文件）中，根据 `task-analysis.md` 的建议使用。开始前需要获得用户批准。

在内部跟踪进度——不要更新此文件。

## 工作流概述

按顺序执行各个阶段。对于大规模任务（6个及以上文件），包括 PRD 阶段。

## 阶段 0: PRD 创建 (仅限大规模任务)

### 阶段前置关卡 [阻塞性 - 未满足无法继续]:
1. **[验证任务跟踪]** 确认任务列表包含此阶段所有必需的 **阻塞性读取 (BLOCKING READs)**
   - 如有任何缺失：暂停 - 返回 `task-analysis.md` 第8步
2. **[阻塞性读取]** 执行对 `.agents/tasks/prd-creation.md` 的读取
3. **[验证]** `prd-creation.md` 在工作内存中处于 **激活** 状态
4. **[验证]** `prd-creation.md` 所要求的所有 skills 都已 **加载** (根据其“所需 skills”部分)
5. **[验证]** `prd-creation.md` 的任务跟踪已完成
6. **[确认]** `prd-creation.md` 中的入口关卡已满足

**强制执行**：在 `prd-creation.md` 确认激活并验证任务跟踪之前，不进行任何需求工作。

### 内部清单:
```
□ 已识别目标用户
□ 已记录用户故事
□ 已定义成功指标
□ 范围边界清晰
□ MoSCoW 优先级排序完成
```

### 可交付成果:
- PRD 文档，路径为 `docs/prd/[feature-name]-prd.md`

### 完成条件:
- 商业价值已阐明
- 用户需求清晰
- 成功标准可衡量

### 停止点: PRD 审查 [阻塞性关卡]
**系统暂停 - 未满足无法继续:**
1. PRD 文档 **存在**于 `docs/prd/[feature]-prd.md`
2. 用户 **明确** 表示批准
3. 所有需求都已理解

**强制执行:**
- 在 PRD 批准之前不进行任何技术设计
- **违规** = 返回 PRD 阶段

## 阶段 1: 需求分析

### 内部清单:
```
□ 已记录用户需求
□ 已列出功能性需求
□ 已识别非功能性需求
□ 已注明约束和假设

```

### 完成条件:
- 需求的所有方面都清晰
- 通过向用户提问解决了模糊之处
- 已定义范围边界

## 阶段 2: 技术设计

### 阶段前置关卡 [阻塞性 - 未满足无法继续]:
1. **[验证任务跟踪]** 确认任务列表包含此阶段所有必需的 **阻塞性读取 (BLOCKING READs)**
   - 如有任何缺失：暂停 - 返回 `task-analysis.md` 第8步
2. **[阻塞性读取]** 执行对 `.agents/tasks/technical-design.md` 的读取
3. **[验证]** `technical-design.md` 在工作内存中处于 **激活** 状态
4. **[验证]** `technical-design.md` 所要求的所有 skills 都已 **加载** (根据其“所需 skills”部分)
5. **[确认]** `technical-design.md` 中的入口关卡已满足

**强制执行**:
- 在 `technical-design.md` 确认激活之前不进行任何设计工作
- 未对 **所有** 阻塞性读取进行任务跟踪验证，则不继续

### 设计前要求:
```
□ 检查是否需要技术决策文档
□ 执行现有代码调查
□ 在线研究最新信息
□ 记录用户协议
```

### 内部清单:
```
□ 如果需要，记录技术决策（参考 technical-design.md）
□ 已选择架构方法
□ 已设计组件结构
□ 已记录数据流
□ 已识别集成点
□ 已证明技术选择的合理性
□ 已定义错误处理策略
□ 已引用参考文献及其 URL
```

### 可交付成果:
- 技术决策文档，位于 `docs/adr/` (如果需要)
- 设计文档，位于 `docs/design/`

### 完成条件:
- 设计涵盖所有需求
- 技术方法清晰
- 实现路径已定义
- 已研究最新的最佳实践

### 停止点: 设计审查 [阻塞性关卡]
**系统暂停 - 未满足无法继续:**
1. 设计文档 **存在**于 `docs/design/[feature]-design.md`
2. **[验证合规性]** 设计文档满足 `technical-design.md` 的 **所有** 要求:
   - `technical-design.md` 的所有完成条件均已满足
   - `technical-design.md` 要求的所有部分均已存在
   - 如不合规：**拒绝** - 返回阶段 2
3. 用户 **明确** 表示批准 ("yes", "approved", "大丈夫", 等)
4. 如果引入了新技术，则创建 ADR

**强制执行:**
- 在收到批准之前不编写任何实现代码
- 未完全遵守任务定义则不继续
- 即使是“简单”的更改也不能跳过
- **违规** = 返回设计阶段

## 阶段 3: 验收测试生成

**阶段顺序理由**：测试骨架 **必须** 在工作规划之前生成。测试结构定义了验证边界，这些边界决定了任务分解的粒度。工作计划文档依赖于这些测试规范，以将实现单元映射到具体的验证点。

### 阶段前置关卡 [阻塞性 - 未满足无法继续]:
1. **[验证任务跟踪]** 确认任务列表包含此阶段所有必需的 **阻塞性读取 (BLOCKING READs)**
   - 如有任何缺失：暂停 - 返回 `task-analysis.md` 第8步
2. **[阻塞性读取]** 执行对 `.agents/tasks/acceptance-test-generation.md` 的读取
3. **[验证]** `acceptance-test-generation.md` 在工作内存中处于 **激活** 状态
4. **[验证]** `acceptance-test-generation.md` 所要求的所有 skills 都已 **加载** (根据其“所需 skills”部分)
5. **[验证]** `acceptance-test-generation.md` 的任务跟踪已完成
6. **[确认]** `acceptance-test-generation.md` 中的入口关卡已满足
7. **[验证]** 设计文档 **存在** 并且包含“验收标准”部分

**强制执行**：在 `acceptance-test-generation.md` 确认激活并验证任务跟踪之前，不生成任何测试。

### 内部清单:
```
□ 已分析设计文档的验收标准
□ 已映射多维度需求
□ 已生成集成测试骨架
□ 已生成 E2E 测试骨架
□ 已使用风险分析分配测试优先级
□ 已记录验证点
□ 已创建可追溯性矩阵
□ 已系统地识别边缘案例
```

### 可交付成果:
- 带有待定/占位符标记的集成测试骨架
- 带有待定/占位符标记的 E2E 测试骨架
- 连接测试与验收标准(ACs)的可追溯性矩阵

### 完成条件:
- 所有验收标准(ACs)都已映射到测试用例
- 遵循了测试框架的约定
- 测试优先级与业务风险一致
- 验证点已清晰记录

### 停止点: 测试骨架审查 [阻塞性关卡]
**系统暂停 - 未满足无法继续:**
1. 测试骨架 **存在**于适当的测试目录中
2. **[验证合规性]** 测试生成满足 `acceptance-test-generation.md` 的 **所有** 要求:
   - `acceptance-test-generation.md` 的所有完成条件均已满足
   - 遵循了测试框架的约定
   - 可追溯性矩阵已完成
   - 如不合规：**拒绝** - 返回阶段 3
3. 用户 **明确** 表示批准测试覆盖方法
4. 生成的测试遵循现有项目模式

**强制执行:**
- 在测试骨架批准之前不进行任何工作规划
- 未遵守测试生成合规性则不继续
- **违规** = 返回测试生成阶段

## 阶段 4: 工作规划

**阶段依赖性**：此阶段 **要求** 阶段 3 完成的测试骨架。任务分解使用测试验证点作为工作单元的边界。每个实现任务都映射到特定的测试用例以进行验证。

### 阶段前置关卡 [阻塞性 - 未满足无法继续]:
1. **[验证任务跟踪]** 确认任务列表包含此阶段所有必需的 **阻塞性读取 (BLOCKING READs)**
   - 如有任何缺失：暂停 - 返回 `task-analysis.md` 第8步
2. **[阻塞性读取]** 执行对 `.agents/tasks/work-planning.md` 的读取
3. **[验证]** `work-planning.md` 在工作内存中处于 **激活** 状态
4. **[验证]** `work-planning.md` 所要求的所有 skills 都已 **加载** (根据其“所需 skills”部分)
5. **[验证]** `work-planning.md` 的任务跟踪已完成
6. **[确认]** `work-planning.md` 中的入口关卡已满足
7. **[验证]** 设计文档已被用户 **批准**
8. **[验证]** 阶段 3 的测试骨架 **存在**于测试目录中

**强制执行**：在 `work-planning.md` 确认激活并验证任务跟踪之前，不创建任何工作计划文档。

### 内部清单:
```
□ 任务已分解为单元
□ 已识别依赖关系
□ 已确定执行顺序
□ 每个任务都有明确的完成标准
□ 已注明风险因素
```

### 可交付成果:
- 带有任务列表的工作计划文档

### 任务分解格式:
```
1. [任务名称]
   - 影响文件:
   - 依赖关系:
   - 完成条件: 当 [特定条件]
   - 状态: [ ] 待定
```

### 停止点: 工作计划批准 [阻塞性关卡]
**系统暂停 - 未编写任何代码无法继续:**
1. 工作计划文档 **存在**于 `docs/plans/YYYYMMDD-{type}-{description}.md`
2. **[验证任务列表]** 任务列表 **必须** 包含 `task-analysis` 第8步中识别的 **所有** 阻塞性读取:
   - 来自工作流阶段的每一个 **阻塞性读取**
   - 来自任务定义的每一个 **阻塞性读取**
   - 来自所需 skills 的每一个 **阻塞性读取**
   - 每个都标记来源: "[来自任务跟踪]"
3. 每个任务都有 **可衡量** 的完成标准
4. 用户 **明确** 批准计划

**关卡验证:**
```
工作计划位置: docs/plans/[filename].md
任务数量: 定义了 [N] 个任务
任务列表中的阻塞性读取: [count] 项
任务跟踪状态: [完成/未完成]
用户批准: [等待中/已收到]
```

**强制执行:**
- 在批准之前 **禁止** 编写第一行代码
- 缺少 **任何** 阻塞性读取 = 返回 `task-analysis` 第8步

## 阶段 5: 实现

### 实现前置关卡 [阻塞性 - 未满足无法开始]:
```
1. [验证任务跟踪] 确认任务列表包含此阶段所有必需的 **阻塞性读取 (BLOCKING READs)**
   - 如有任何缺失：暂停 - 返回 `task-analysis.md` 第8步
2. [阻塞性读取] 执行对 `.agents/tasks/implementation.md` 的读取
3. [验证] `implementation.md` 在工作内存中处于 **激活** 状态
4. [验证] `implementation.md` 所要求的所有 skills 都已 **加载** (根据其“所需 skills”部分)
5. [验证] `implementation.md` 的任务跟踪已完成
6. [确认] `implementation.md` 中的入口关卡已满足
7. [验证] 工作计划文档 **存在** 并已被 **批准**
8. [确认] 已从工作计划文档中识别当前任务
```

**关键强制执行**:
- 在 `implementation.md` 确认激活之前，代码行数为 **零**
- 没有通过关卡就进行首次代码尝试 = **立即删除**
- 违规将被记录，并要求从阶段 5 的关卡重新开始

### 执行模式 [强制顺序]:
```
对于工作计划文档中的每个任务:
  1. [元认知前] 执行元认知协议中的“开始工作时”清单
  2. [跟踪] 在你的内部任务管理（任务列表）中将任务标记为 `in_progress`
  3. [实现] 遵循所有已加载的 skills 编写代码 (TDD: 红-绿-重构)
  4. [验证] 运行 **所有** 质量检查命令 - **必须** 有 0 个错误
  5. [提交] 为此任务进行带有描述性消息的 Git 提交
  6. [更新] 在工作计划文档中将任务复选框标记为完成 `[x]`
  7. [关卡检查] **所有** 完成标准必须通过
  8. [元认知后] 执行“完成后”清单
  9. [跟踪] 在任务列表中将任务标记为完成
  10. [检查点] 在所有步骤完成之前不能开始下一个任务
```

**强制执行:**
- 跳过 **任何** 步骤 = **重新开始** 任务
- 未加载 `implementation.md` 则不编写代码
- 未进行元认知则不进行任务转换

### 指南:
- 在开始下一个任务之前完全完成一个任务
- 随实现随测试每个组件
- 记录重要决策
- 遇到障碍时询问用户

**强制执行**：在 `quality-assurance.md` 确认激活并验证任务跟踪之前，不进行任何质量检查。

### 内部清单:
