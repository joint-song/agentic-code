# 实施策略选择框架 (元认知方法)

一个基于元认知思维的实施策略选择框架。通过从理解现有实施到约束兼容性的系统化决策过程，推导出最佳的实施方法。

## 元认知策略选择过程

### 步骤 1: 全面的现状分析

**核心问题**: “现有的实施是什么样的？”

#### 分析框架
```yaml
架构分析:
  - 当前的职责分离和改进潜力
  - 数据流识别和评估
  - 依赖关系可视化和影响范围
  - 技术债务量化

实施质量评估:
  - 代码质量和可维护性
  - 测试覆盖率和可靠性
  - 性能特征
  - 安全考虑

历史背景理解:
  - 为什么会变成现在的形式？
  - 过去决策的有效性检查
  - 技术约束的变化
  - 业务需求的演变
```

#### 元认知问题列表
- 这个实施的真正职责是什么？
- 哪些部分是业务本质，哪些源于技术约束？
- 代码中哪些依赖或隐式前提条件不明确？
- 当前设计带来了哪些好处和约束？

### 步骤 2: 策略探索与创造

**核心问题**: “在确定 before → after 时，应该参考哪些实施模式或策略？”

#### 策略发现过程
```yaml
研究与探索:
  - 来自类似技术栈的实施示例和模式 (在线研究)
  - 从处理类似挑战的项目中收集方法
  - 开源实施参考
  - 技术文献和博客研究

创造性思维:
  - 多种策略的顺序/并行应用
  - 基于项目时间/人力/技术约束的设计
  - 阶段划分和里程碑设置
  - 必要扩展点的预先设计
```

#### 参考策略模式 (鼓励创造性组合)

**遗留系统处理策略**:
- 绞杀者模式 (Strangler Pattern): 通过分阶段替换逐步迁移
- 外观模式 (Facade Pattern): 通过统一接口隐藏复杂性
- 适配器模式 (Adapter Pattern): 与现有系统桥接

**新开发策略**:
- 功能驱动开发 (Feature-driven Development): 优先考虑用户价值的垂直实施
- 基础驱动开发 (Foundation-driven Development): 优先考虑稳定性的基础先行建设
- 风险驱动开发 (Risk-driven Development): 优先解决最大风险元素

**集成/迁移策略**:
- 代理模式 (Proxy Pattern): 透明的功能扩展
- 装饰器模式 (Decorator Pattern): 对现有功能的分阶段增强
- 桥接模式 (Bridge Pattern): 通过抽象实现灵活性

**重要提示**: 最佳解决方案是通过根据每个项目的背景进行创造性思维来发现的。

### 步骤 3: 风险评估与控制

**核心问题**: “将此应用于现有实施时会出现哪些风险，以及控制它们的最佳方法是什么？”

#### 风险分析矩阵
```yaml
技术风险:
  - 对现有系统的影响
  - 数据一致性保证
  - 性能下降的可能性
  - 集成复杂性

运营风险:
  - 对服务可用性的影响
  - 部署停机时间
  - 监控/运营流程变更
  - 故障回滚程序

项目风险:
  - 进度延迟的可能性
  - 技术学习成本
  - 质量要求达成
  - 跨团队协调复杂性
```

#### 风险控制策略
```yaml
预防措施:
  - 在不中断服务的情况下分阶段迁移到新系统
  - 通过新旧系统并行运行进行验证
  - 为新功能添加集成和回归测试
  - 实施前设置性能和错误监控

事件响应:
  - 明确回滚到旧系统的程序和条件
  - 准备日志分析和指标仪表板
  - 定义故障时的通信系统和角色分配
  - 记录部分服务延续程序
```

### 步骤 4: 约束兼容性验证

**核心问题**: “这个项目的约束是什么？”

#### 约束清单
```yaml
技术约束:
  - 与现有库/框架的兼容性
  - 服务器资源、网络、数据库容量限制
  - 数据保护、访问控制、审计日志等强制性要求
  - 响应时间 <5秒, 99.9% 正常运行时间等数值目标

时间约束:
  - 项目截止日期和优先级
  - 与其他项目的依赖关系
  - 里程碑/发布计划
  - 学习/获取周期的考虑

资源约束:
  - 团队规模、新技术学习时间、现有 skill 集
  - 开发人员工作时间、服务器资源、运营系统分配
  - 项目预算上限、运行成本上限
  - 外部供应商支持截止日期、SLA、合同条款

业务约束:
  - 市场上市时间要求
  - 客户影响最小化要求
  - 法规/行业标准合规性
```

### 步骤 5: 实施方法决策

从基本的实施方法中选择最佳解决方案 (鼓励创造性组合)：

#### 垂直切片 (功能驱动)
**特点**: 按功能单元跨所有层进行垂直实施
**应用条件**: 功能间依赖性低，以用户可用的形式输出，需要在所有架构层进行更改
**验证方法**: 每个功能完成时交付最终用户价值

#### 水平切片 (基础驱动)
**特点**: 按架构层分阶段构建
**应用条件**: 基础系统的稳定性很重要，多个功能依赖于共同的基础，逐层验证有效
**验证方法**: 所有基础层完成后进行集成操作验证

#### 混合 (创造性组合)
**特点**: 根据项目特点灵活组合
**应用条件**: 需求不明确，需要根据阶段改变方法，从原型过渡到完全实施
**验证方法**: 根据每个阶段的目标在适当的 L1/L2/L3 级别进行验证

### 步骤 6: 决策理由文档化

**设计文档文档化**: 清晰地说明实施策略选择的原因和理由。

## 验证级别定义

每个任务完成验证的优先级：

- **L1: 功能操作验证** - 作为最终用户功能运行 (例如，可执行的搜索)
- **L2: 测试操作验证** - 添加了新测试并通过 (例如，类型定义测试)
- **L3: 构建成功验证** - 没有编译错误 (例如，接口定义)

**优先级**: L1 > L2 > L3 (按可验证性重要性排序)

## 集成点定义

根据所选策略定义集成点：
- **基于绞杀者模式**: 每个功能在新旧系统之间切换时
- **功能驱动**: 当用户可以实际使用该功能时
- **基础驱动**: 当所有架构层都准备好并通过 E2E 测试时
- **混合**: 当为每个阶段定义的个别目标实现时

## 反模式

- **模式固化**: 仅从列出的策略中选择，而不考虑独特的组合
- **分析不足**: 在策略选择前跳过步骤 1 的分析框架
- **风险忽视**: 在没有步骤 3 风险分析矩阵的情况下开始实施
- **约束无视**: 在未检查步骤 4 约束清单的情况下决定策略
- **理由省略**: 在不使用步骤 6 文档模板的情况下选择策略

## 元认知执行指南

1.  **利用已知模式**: 作为起点，探索创造性的组合
2.  **积极的网络研究**: 研究来自类似技术栈的实施示例
3.  **应用“五个为什么”**: 追溯根本原因以掌握本质
4.  **多角度评估**: 从步骤 1-4 的每个角度全面评估
5.  **创造性思维**: 考虑多种策略的顺序应用和利用项目特定约束的设计
6.  **明确决策理由**: 在设计文档中明确说明策略选择的理由
