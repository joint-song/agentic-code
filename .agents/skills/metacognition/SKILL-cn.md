# 元认知协议

## 目的

自我评估检查点。

## 何时应用 [强制性检查点]

**在以下节点必须进行阻塞性元认知：**
- [检查点] 任务类型变更 → **未经评估不能继续**
- [检查点] 完成工作计划文档中的 **任何** 任务后 → **在下一任务前必须评估**
- [检查点] 遇到错误或意外结果时 → **立即评估方法**
- [检查点] 编写新功能的第一行代码之前 → **首先验证方法**
- [检查点] 在主要阶段之间切换时 → **确认所有关卡已通过**

**强制执行**：跳过元认知 = **严重违规**

## 评估问题

### 1. 任务理解

- 根本目标是什么？
- 我是在解决根本原因还是表面症状？
- 我是否拥有所有必要信息？
- 成功标准是否清晰且可衡量？
- 在这一点上，已知的未知是什么？

### 2. 当前状态

- 当前加载了哪些 skills？
- 哪些 skills 实际被使用？
- 我正在做出哪些假设？
- 可能会出现什么问题？

### 3. 方法验证

- 我的方法是“最简单”的解决方案吗？
- 我是否在遵循既定模式？
- 我是否考虑过替代方案？
- 这在长期内是否可维护？
- 什么会让我推翻这个决定？(终止标准)

## 反模式识别

| 模式 | 迹象 | 纠正 |
|---------|-------|------------|
| **过度工程** | 简单问题的复杂解决方案 | 简化方法 |
| **计划不足** | 过快地投入编码 | 退后一步，先规划 |
| **隧道视野** | 忽略替代方案 | 考虑其他方法 |
| **质量债务** | 跳过测试或文档 | 正确地完成 |
| **上下文膨胀** | 加载不必要的 skills | 只加载必需的 |

## 错误恢复

当卡住时：
1. 识别是什么阻碍了进展
2. 检查是知识差距还是逻辑错误
3. 审查已加载的 skills 以获取指导
4. 考虑更简单的方法
5. 请求用户澄清

**错误处理协议：**

当遇到错误或阻塞时：
- [立即] 执行元认知评估
- [搜索] 在代码库中寻找相似模式
- [重读] 相关 skill 文件以获取指导
- [评估] 我能用现有信息解决这个问题吗？

如果无法解决：
- [记录] 确切的错误消息和上下文
- [解释] 尝试了什么以及为什么失败
- [请求] 带有具体问题的用户指导

**原则：在真正卡住时请求帮助，而不是在任意尝试次数后**

## 从经验中学习

跟踪：
- 哪些方法效果好
- 是什么导致了延迟
- 哪些 skills 有帮助
- 出现了哪些模式
- 下次可以做些什么不同的事

## 指南

- **诚实**：承认不确定的时候
- **系统化**：遵循结构化的方法
- **高效**：不要过度思考简单的任务
- **彻底**：不要跳过重要的步骤
- **适应性强**：根据反馈调整方法

## 注意

记住：
- 元认知可以防止代价高昂的错误
- 定期反思可以提高质量
- 停下来思考是可以的
- 在真正卡住时请求帮助
- 完美是优秀的敌人
