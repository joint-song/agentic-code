# AI 开发者指南

## 技术反模式 (危险信号模式)

在检测到以下模式时，立即停止并重新考虑设计：

### 代码质量反模式
1. **编写类似代码3次或以上**
2. **单个文件中混合了多种职责**
3. **在多个文件中定义相同内容**
4. **不检查依赖关系就进行更改**
5. **用注释禁用代码**
6. **错误抑制**

### 设计反模式
- **“暂时能用就行”的想法**
- **打补丁式的实现**
- **对不确定的技术进行乐观的实现**
- **治标不治本的修复**
- **无计划的大规模更改**

## 快速失败回退设计原则

### 核心原则
优先保证主代码的可靠性，而非回退实现。在分布式系统中，过多的回退机制会掩盖错误，使调试变得困难。

### 实现指南

#### 默认方法
- **明确失败优于静默默认**: 错误必须可见且可追溯，不能被自动的默认值掩盖
- **保留错误上下文**: 重新抛出错误时包含原始错误信息

#### 何时可以接受回退
- **仅在有明确的设计文档批准时**: 记录为什么回退是必要的
- **业务关键的连续性**: 当部分功能优于完全没有功能时
- **优雅降级路径**: 清晰定义的服务降级级别

#### 分层职责
- **基础设施层**:
  - 始终向上抛出错误
  - 不做业务逻辑决策
  - 提供详细的错误上下文

- **应用层**:
  - 做出由业务驱动的错误处理决策
  - 仅在需求中指定时实现回退
  - 记录所有回退激活以供监控

### 错误掩盖检测

**审查触发器** (需要设计审查)：
- 在同一功能中编写第3个错误处理块
- 单个函数中有多个错误处理结构
- 嵌套的错误处理结构
- 返回默认值而不传播的错误处理器

**在实现任何回退之前**:
1. 验证设计文档是否明确定义了此回退
2. 记录业务理由
3. 确保错误被完整地记录了上下文
4. 为回退激活添加监控/警报

### 实现模式

注意：使用你语言的标准错误处理机制 (异常、Result 类型、错误值等)

```
❌ 避免：隐藏错误的静默回退
    [处理错误]:
        return DEFAULT_USER  // 错误被隐藏，调试变得困难

✅ 推荐：带有上下文的明确失败
    [处理错误]:
        logError('无法获取用户数据', userId, error)
        propagate ServiceError('用户数据不可用', error)

✅ 可接受：有文档记录和监控的回退 (在设计文档中有理由时)
    [处理错误]:
        // 回退在设计文档 3.2.1 节中定义
        logWarning('主数据源失败，使用缓存', error)
        incrementMetric('data.fallback.cache_used')

        cachedData = fetchFromCache()
        if not cachedData:
            propagate ServiceError('主数据源和缓存均失败', error)
        return cachedData
```

## 三次法则 - 代码重复的标准

| 重复次数 | 行动 | 原因 |
|-------------------|--------|--------|
| 第1次 | 内联实现 | 无法预测未来的变化 |
| 第2次 | 考虑未来进行整合 | 模式开始出现 |
| 第3次 | 实现通用化 | 模式已确立 |

### 通用化标准

**通用化的情况**
- 业务逻辑重复
- 复杂的处理算法
- 可能需要批量更改的区域
- 验证规则

**避免通用化的情况**
- 偶然匹配 (碰巧相同的代码)
- 可能向不同方向演变
- 通用化导致可读性显著下降
- 测试代码中的简单辅助函数

### 实现示例
```
// ❌ 差: 在第1次重复时立即通用化
function validateUserEmail(email) { /* ... */ }
function validateContactEmail(email) { /* ... */ }
// → 过早的抽象

// ✅ 好: 在第3次出现时通用化
// 第1次: 内联实现
// 第2次: 复制但考虑未来
// 第3次: 提取到通用验证器
function validateEmail(email, context) { /* ... */ }
```

## 常见失败模式及避免方法

### 模式 1: 错误修复链
**症状**: 修复一个错误导致新错误
**原因**: 未理解根本原因的表面修复
**避免方法**: 在修复前使用“五个为什么”识别根本原因

### 模式 2: 没有充分测试的实现
**症状**: 实现后出现许多错误
**原因**: 忽略红-绿-重构过程
**避免方法**: 始终从失败的测试开始

### 模式 4: 忽略技术不确定性
**症状**: 引入新技术时频繁出现意外错误
**原因**: 在没有事先调查的情况下假设“根据官方文档应该可以工作”
**避免方法**:
- 在任务文件开头记录确定性评估
  ```
  确定性: 低 (原因: 未找到 MCP 连接的示例)
  探索性实现: 是
  回退方案: 使用传统 API
  ```
- 对于低确定性的情况，首先创建最小的验证代码

### 模式 5: 现有代码调查不足
**症状**: 重复实现、架构不一致、集成失败
**原因**: 实现前对现有代码理解不足
**避免方法**:
- 实现前，始终搜索相似功能 (使用领域、职责、配置模式作为关键字)
- 找到相似功能 → 使用该实现 (不创建新实现)
- 相似功能是技术债务 → 在实现前创建 ADR 改进提案
- 不存在相似功能 → 遵循现有设计理念实现新功能
- 在设计文档的“现有代码库分析”部分记录所有决策和理由

## 调试技巧

### 1. 错误分析程序
```bash
# 如何阅读堆栈跟踪
1. 准确阅读错误消息 (第一行)
2. 关注堆栈跟踪的开头和结尾
3. 识别你的代码出现的第一行
```

### 2. 五个为什么 - 根本原因分析
```
症状: 应用程序启动时崩溃
为什么1: 配置加载失败 → 为什么2: 配置文件格式改变
为什么3: 依赖更新 → 为什么4: 库的重大变更
为什么5: 未约束的依赖版本规范
根本原因: 不恰当的版本管理策略
```

### 3. 最小复现代码
为了隔离问题，尝试用最少的代码复现：
- 移除不相关的部分
- 用模拟替换外部依赖
- 创建能复现问题的最小配置

### 4. 调试日志输出
```
// 用结构化日志跟踪问题
log('DEBUG:', {
  context: 'user-creation',
  input: { email, name },
  state: currentState,
  timestamp: currentTimestamp()
})
```

## 需要技术决策的情景

### 抽象的时机
- 在编写具体实现3次后提取模式
- 注意 YAGNI，只实现当前需要的功能
- 优先考虑当前的简单性而非未来的扩展性

### 性能 vs 可读性
- 除非存在明确的瓶颈，否则优先考虑可读性
- 在优化前测量 (不要猜测，要测量)
- 在优化时用注释记录原因

## 持续改进的心态

- **谦逊**: 完美的代码不存在，欢迎反馈
- **勇气**: 大胆执行必要的重构
- **透明**: 清晰地记录技术决策的理由

## 实施完整性保证

### 影响分析：强制性的三阶段过程

在任何实现之前，按顺序完成这些阶段：

**1. 发现** - 识别所有受影响的代码：
- 实现引用 (导入, 调用, 实例化)
- 接口依赖 (契约, 类型, 数据结构)
- 测试覆盖率
- 配置 (构建配置, 环境设置, 功能标志)
- 文档 (注释, 文档, 图表)

**2. 理解** - 分析每个发现的位置：
- 在系统中的角色和目的
- 依赖方向 (消费者或提供者)
- 数据流 (来源 → 转换 → 目的地)
- 耦合强度

**3. 识别** - 生成结构化报告：
```
## 影响分析
### 直接影响
- [单元]: [原因和需要的修改]

### 间接影响
- [系统]: [集成路径 → 原因]

### 数据流
[来源] → [转换] → [消费者]

### 风险评估
- 高: [复杂的依赖, 脆弱的区域]
- 中: [中等耦合, 测试缺口]
- 低: [隔离的, 测试良好的区域]

### 实现顺序
1. [从最低风险或最深依赖开始]
2. [...]
```

**关键**: 在所有3个阶段都记录下来之前不要实现

**与模式5的关系**: 这个过程提供了避免“现有代码调查不足”的结构化方法

### 未使用代码的删除

当检测到未使用的代码时：
- 这次工作中会用到吗？ 是 → 立即实现 | 否 → 立即删除 (Git 会保留)
- 适用于：代码、测试、文档、配置、资源

### 现有代码的修改

```
在使用中吗？ 否 → 删除
           是 → 能工作吗？ 否 → 删除 + 重新实现
                       是 → 修复/扩展
```

**原则**: 倾向于干净的实现，而非修补损坏的代码
