## TDD 流程 [对所有代码变更强制执行]

**对每次代码变更执行此流程：**

### 红 (RED) 阶段
1. 编写定义预期行为的测试
2. 运行测试
3. 确认测试 **失败** (如果通过，则测试是错误的)

### 绿 (GREEN) 阶段
1. 编写 **最少** 的代码使测试通过
2. 运行测试
3. 确认测试 **通过**

### 重构 (REFACTOR) 阶段
1. 提高代码质量
2. 运行测试
3. 确认测试 **仍然通过**

### 验证 (VERIFY) 阶段 [强制性 - 要求 0 错误]
1. 执行你的语言/项目的所有质量检查命令
2. 修复任何错误，直到 **所有** 命令都以 0 错误通过
3. 确认没有回归
4. **强制执行**：不能在有 **任何** 错误或警告的情况下继续

**例外情况 (不需要 TDD)：**
- 纯配置文件
- 仅文档
- 紧急修复 (但之后应立即添加测试)
- 探索性工作 (在合并前丢弃或用测试重写)
- 构建/部署脚本 (除非它们包含业务逻辑)

## 基本测试策略

### 质量要求
- **覆盖率**：单元测试覆盖率必须达到 80% 或更高
- **独立性**：每个测试都可以独立运行
- **可复现性**：测试与环境无关

### 覆盖率要求
**强制性**：单元测试覆盖率必须达到 80% 或更高
**指标**：语句、分支、函数、行

### 测试类型与范围
1. **单元测试**
   - 验证单个单元（函数、模块或组件）的行为
   - 模拟所有外部依赖
   - 快速执行 (毫秒级)

2. **集成测试**
   - 验证多个组件之间的协调
   - 适当时使用实际依赖
   - 测试真实的系统交互

3. **E2E 测试 (端到端测试)**
   - 验证整个系统中完整的用户工作流
   - 使用所有集成的组件测试真实世界场景
   - 从用户角度验证系统行为
   - 确保端到端满足业务需求

4. **E2E 测试中的跨功能验证** [对于功能修改是强制性的]

   **目的**：在引入新功能或修改时，防止回归并确保现有功能的稳定性。

   **何时需要**：
   - 添加与现有组件交互的新功能
   - 修改核心业务逻辑或工作流
   - 更改共享资源或数据结构
   - 更新 API 或集成点

   **集成点分析**：
   - **高影响**：核心流程变更、重大变更或工作流修改
     - 强制要求全面的 E2E 测试覆盖
     - 需要完整的回归测试套件
     - 前后进行性能基准测试

   - **中等影响**：数据使用修改、共享状态变更或新的依赖关系
     - 最低要求是集成测试
     - 针对受影响工作流的定向 E2E 测试
     - 强制要求覆盖边缘案例

   - **低影响**：只读操作、添加日志或监控钩子
     - 单元测试覆盖足够
     - 对集成点进行冒烟测试

   **成功标准**：
   - 现有工作流中无重大变更
   - 性能下降在项目定义的“可接受”范围内
   - 先前稳定的功能中没有新错误
   - 所有集成点保持预期的契约
   - 在需要时保持向后兼容性

## 测试设计原则

### 测试用例结构
- 测试由三个阶段组成：**准备 (Setup)、执行 (Execute)、验证 (Verify)** (也称为 Arrange-Act-Assert 或 Given-When-Then)
- 清晰的命名，显示每个测试的目的
- 一个测试用例只验证一个行为
- 测试名称应描述预期行为，而非实现

### 测试数据管理
- 在专用目录中管理测试数据
- 定义特定于测试的配置值
- 始终模拟敏感信息 (密码、令牌、API 密钥)
- 保持测试数据最少，只使用与测试用例验证直接相关的数据

### 测试独立性
- 每个测试都应能在隔离环境中运行
- 测试不应依赖于执行顺序
- 每个测试后清理测试状态
- 避免测试之间共享可变状态

## Mock 和 Stub 使用策略

✅ **推荐：在单元测试中模拟外部依赖**
- 优点：确保测试的独立性和可复现性
- 实践：模拟数据库、API、文件系统和其他外部依赖
- 使用适合框架的模拟工具

❌ **避免：在单元测试中进行实际的外部连接**
- 原因：减慢测试速度并导致环境相关的问题
- 例外：专门测试外部集成的集成测试

### Mock 决策标准
| Mock 特性 | 响应策略 |
|---------------------|-----------------|
| **简单且稳定** | 在通用辅助函数中整合 |
| **复杂或频繁变化** | 单独实现 |
| **在3个以上地方重复** | 考虑整合 |
| **特定于测试的逻辑** | 单独实现 |

## 测试粒度原则

### 核心原则：仅限可观察的行为
**必须测试**：
- 公共 API 和契约
- 返回值和输出
- 异常和错误条件
- 外部调用和副作用
- 持久化状态的变更

**禁止测试**：
- 未公开暴露的内部实现细节
- 从外部不可观察的内部状态
- 算法实现细节
- 框架/库的内部

### 测试失败响应决策标准

**在以下情况修复测试：**
- 预期值错误
- 测试引用了不存在的功能
- 测试依赖于实现细节
- 测试仅为覆盖率而编写

**在以下情况修复实现：**
- 测试代表了有效的规范
- 业务逻辑需求已更改
- 重要的边缘案例失败

**如有疑问**：与利益相关者或领域专家确认

## 测试实现最佳实践

### 命名约定
- 测试文件：遵循你的语言/框架约定
- 测试套件：描述目标功能或情景的名称
- 测试用例：描述预期行为（而非实现）的名称

### 测试代码质量规则

✅ **推荐：始终保持所有测试激活**
- 优点：保证测试套件的完整性
- 实践：修复有问题的测试并激活它们

❌ **避免：跳过或注释掉测试**
- 原因：造成测试缺口和不完整的质量检查
- 解决方案：修复测试，如果确实不需要则完全删除

## 测试质量标准 [强制性]

1. **边界覆盖**：包含空/零/最大/错误案例以及正常路径
2. **字面量期望**：在断言中使用字面量值，而不是计算表达式
   - 期望值 ≠ 模拟返回值 (实现会处理数据)
3. **结果验证**：断言返回值和状态，而非调用顺序
4. **有意义的断言**：每个测试必须至少有一个断言
5. **仅模拟外部 I/O**：模拟数据库/API/文件系统，使用真实的内部工具

### 测试辅助函数指南

**基本原则**
测试辅助函数应减少重复并提高可维护性。

**使用示例**
- 用于创建测试数据的构建者模式
- 用于领域特定验证的自定义断言
- 共享的设置/拆卸工具
- 通用的模拟配置

## 质量检查命令 [验证 (VERIFY) 阶段强制执行]

**执行适合你的语言和项目设置的质量检查：**

### 必需的质量检查
你的项目 **必须** 有机制来验证：

1. **所有测试通过**
   - 单元测试成功执行
   - 集成测试 (如适用) 通过
   - 没有测试失败或错误

2. **代码成功构建**
   - 编译成功 (对于编译型语言)
   - 没有构建错误或警告

3. **代码风格合规**
   - 满足 Linting 规则
   - 符合格式化标准
   - 验证了风格指南的遵守情况

4. **类型安全** (对于类型化语言)
   - 类型检查通过
   - 没有类型错误或警告

### 强制执行
- 如果 **任何** 质量检查失败，则不能继续完成任务
- 在将任务标记为完成之前，必须修复所有错误和警告
- 如果你的项目缺少某些质量工具，请建立它们或记录此差距
