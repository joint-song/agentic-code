# 文档创建标准

## 创建决策矩阵

| 条件 | 所需文档 | 创建顺序 |
|-----------|-------------------|----------------|
| 新功能添加 | PRD → [ADR] → 设计文档 → 工作计划 | PRD 批准后 |
| 满足 ADR 条件 (见下文) | ADR → 设计文档 → 工作计划 | 立即开始 |
| 6个及以上文件 | ADR → 设计文档 → 工作计划 (必需) | 立即开始 |
| 3-5个文件 | 设计文档 → 工作计划 (推荐) | 立即开始 |
| 1-2个文件 | 无 | 直接实现 |

## ADR 创建条件 (任何一项适用则为必需)

### 1. 类型系统变更
- **添加3层及以上的嵌套类型/结构**: 例如 `A { B { C { D } } }`
  - 理由: 深度嵌套具有高复杂性和广泛的影响范围
- **更改/删除在3个及以上位置使用的类型**
  - 理由: 多处影响需要仔细考虑
- **数据表示职责变更** (例如，传输对象→领域模型)
  - 理由: 概念模型的变更影响设计哲学

### 2. 数据流变更
- **存储位置变更** (数据库→文件, 内存→缓存)
- **包含3个及以上步骤的处理顺序变更**
  - 示例: "输入→验证→保存" 变为 "输入→保存→异步验证"
- **数据传递方式变更** (props→Context, 直接引用→事件)

### 3. 架构变更
- 层级添加、职责变更、组件重定位

### 4. 外部依赖变更
- 引入或替换库/框架/外部 API

### 5. 复杂的实现逻辑 (无论规模大小)
- 管理3个及以上的状态
- 协调5个及以上的异步过程

## 详细文档定义

### PRD (产品需求文档)

**目的**: 定义业务需求和用户价值

**包含**:
- 业务需求和用户价值
- 成功指标和 KPI (可衡量格式)
- 用户故事和用例
- MoSCoW 优先级 (必须/应该/可以/不会)
- MVP 和未来阶段的分离
- 用户旅程图
- 范围边界图

**不包含**:
- 技术实现细节 (→设计文档)
- 技术选型理由 (→ADR)
- **实现阶段** (→工作计划)
- **任务分解** (→工作计划)

### ADR (架构决策记录)

**目的**: 记录技术决策

**包含**:
- 决策 (选择了什么)
- 理由 (为什么做出该选择)
- 选项比较 (最少3个选项) 和权衡
- 架构影响
- 基于原则的实现指南

**不包含**:
- 实现时间表、持续时间 (→工作计划)
- 详细的实现步骤 (→设计文档)
- 特定的代码示例 (→设计文档)
- 资源分配 (→工作计划)

### 设计文档

**目的**: 定义技术实现

**包含**:
- **现有代码库分析** (必需)
  - 实现路径映射 (包括现有和新的)
  - 集成点澄清 (即使是新实现，也需明确与现有代码的连接点)
- 技术实现方法 (垂直/水平/混合)
- **技术依赖和实现约束** (必需的实现顺序)
- 接口和类型定义
- 数据流和组件设计
- **集成点的 E2E 验证程序**
- **验收标准 (可衡量格式)**
- 变更影响图 (明确说明直接影响/间接影响/无连锁反应)
- 集成点的完整枚举
- 数据契约澄清
- **协议清单** (与利益相关者的协议)
- **代码检查证据** (调查期间检查的文件/函数)
- **字段传播图** (当字段跨越组件边界时)
- **数据表示决策** (当引入新结构时)
- **适用标准** (显式/隐式分类)
- **先决 ADR** (包括通用 ADR)

**必需的结构元素**:
```yaml
变更影响图:
  变更目标: [组件/功能]
  直接影响: [文件/函数]
  间接影响: [数据格式/处理时间]
  无连锁反应: [未受影响的功能]

API 契约变更矩阵:
  现有: [函数/操作签名]
  新的: [函数/操作签名]
  需要转换: [是/否]
  兼容性策略: [方法]
```

**不包含**:
- 为什么选择该技术 (→参考 ADR)
- 何时实现、持续时间 (→工作计划)
- 由谁实现 (→工作计划)

### 工作计划

**目的**: 实现任务管理和进度跟踪

**包含**:
- 任务分解和依赖关系 (最多2层)
- 时间表和持续时间估算
- **从设计文档复制 E2E 验证程序** (不能删除, 可以添加)
- **阶段 4 质量保证阶段 (必需)**
- 进度记录 (复选框格式)

**不包含**:
- 技术理由 (→ADR)
- 设计细节 (→设计文档)

**阶段划分标准**:
1. **阶段 1: 基础实现** - 类型定义、接口、测试准备
2. **阶段 2: 核心功能实现** - 业务逻辑、单元测试
3. **阶段 3: 集成实现** - 外部连接、表示层
4. **阶段 4: 质量保证 (必需)** - 验收标准达成、所有测试通过、质量检查

**任务完成定义的三要素**:
1. **实现完成**: 代码功能正常
2. **质量完成**: 测试、类型检查、Linting 通过
3. **集成完成**: 与其他组件的连接已验证

## 创建过程

1. **问题分析**: 变更规模评估, ADR 条件检查
   - 在调查前识别显式和隐式的项目标准
2. **ADR 选项考虑** (仅 ADR): 比较3个以上选项, 指明权衡
3. **创建**: 使用模板, 包含可衡量的条件
4. **批准**: 审查后“已接受”状态方可实现

## 存储位置

| 文档 | 路径 | 命名约定 | 模板 |
|----------|------|------------------|----------|
| PRD | `docs/prd/` | `[功能名称]-prd.md` | `template-en.md` |
| ADR | `docs/adr/` | `ADR-[4位数字]-[标题].md` | `template-en.md` |
| 设计文档 | `docs/design/` | `[功能名称]-design.md` | `template-en.md` |
| 工作计划 | `docs/plans/` | `YYYYMMDD-{类型}-{描述}.md` | `template-en.md` |

*注意: 工作计划存储在 `docs/plans/` 中，并被 `.gitignore` 排除*

## ADR 状态
`提议中` → `已接受` → `已弃用`/`已取代`/`已拒绝`

## AI 自动化规则
- 5个及以上文件: 建议创建 ADR
- 检测到类型/数据流变更: ADR 强制
- 在实现前检查现有的 ADR

## 图表要求

每个文档所需的图表 (使用 mermaid 表示法)：

| 文档 | 所需图表 | 目的 |
|----------|------------------|---------|
| PRD | 用户旅程图, 范围边界图 | 澄清用户体验和范围 |
| ADR | 选项比较图 (需要时) | 可视化权衡 |
| 设计文档 | 架构图, 数据流图 | 理解技术结构 |
| 工作计划 | 阶段结构图, 任务依赖图 | 澄清实现顺序 |

## 通用 ADR 关系
1. **创建时**: 识别通用技术领域 (日志记录、错误处理、异步处理等), 引用现有的通用 ADR
2. **缺失时**: 考虑创建必要的通用 ADR
3. **设计文档**: 在“先决 ADR”部分指明通用 ADR
4. **合规性检查**: 验证设计是否与通用 ADR 决策一致
