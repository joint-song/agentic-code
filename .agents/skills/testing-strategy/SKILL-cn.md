# 测试策略：基于 ROI 的选择

## 核心原则：最大化覆盖，最小化测试

**理念**：10个可靠的测试 > 100个无人维护的测试

质量重于数量 - 将资源集中在高价值的测试上，以最小的维护负担提供最大的覆盖范围。

## ROI 计算框架

### ROI 公式

```
ROI 分数 = (业务价值 × 用户频率 + 法律要求 × 10 + 缺陷检测)
            / (创建成本 + 执行成本 + 维护成本)
```

### 价值组成部分

**业务价值** (0-10分):
- 10: 收入关键型 (支付处理, 结账)
- 8-9: 核心业务功能 (用户注册, 数据持久化)
- 5-7: 重要的次要功能 (搜索, 过滤)
- 2-4: 锦上添花的功能 (UI 增强)
- 0-1: 外观性功能

**用户频率** (0-10分):
- 10: 每个用户，每个会话 (认证)
- 8-9: >80% 的用户定期使用
- 5-7: 50-80% 的用户偶尔使用
- 2-4: <50% 的用户很少使用
- 0-1: 仅边缘案例用户

**法律要求** (布尔值 → 0 或 1):
- 1: 法律强制要求 (GDPR 合规, 数据保护)
- 0: 非法律要求

**缺陷检测** (0-10分):
- 10: 极有可能捕获关键错误
- 5-7: 中等可能捕获错误
- 0-4: 低可能 (逻辑简单, 已充分测试的模式)

### 成本组成部分

**测试级别成本表**:

| 测试级别 | 创建成本 | 执行成本 | 维护成本 | 总成本 |
|-------------|---------------|----------------|------------------|------------|
| 单元 | 1 | 1 | 1 | 3 |
| 集成 | 3 | 5 | 3 | 11 |
| E2E | 10 | 20 | 8 | 38 |

**成本理由**:
- **单元测试**: 编写快, 运行快, 很少因重构而损坏
- **集成测试**: 设置中等, 执行较慢, 维护中等
- **E2E 测试**: 设置复杂, 执行非常慢, 脆弱性高 (比单元测试贵12倍)

### ROI 计算示例

**示例 1: 支付处理集成测试**
```
业务价值: 10 (收入关键型)
用户频率: 9 (90% 的用户)
法律要求: 0
缺陷检测: 8 (高复杂度)

ROI = (10 × 9 + 0 + 8) / 11 = 98 / 11 = 8.9
决策: 高 ROI → 生成此测试
```

**示例 2: UI 主题切换 E2E 测试**
```
业务价值: 2 (外观性功能)
用户频率: 5 (50% 的用户)
法律要求: 0
缺陷检测: 3 (逻辑简单)

ROI = (2 × 5 + 0 + 3) / 38 = 13 / 38 = 0.34
决策: 低 ROI → 跳过此 E2E 测试 (考虑改为单元测试)
```

**示例 3: GDPR 数据删除 E2E 测试**
```
业务价值: 8 (关键合规性)
用户频率: 1 (罕见的用户操作)
法律要求: 1 (法律强制)
缺陷检测: 9 (如果损坏后果严重)

ROI = (8 × 1 + 1 × 10 + 9) / 38 = 27 / 38 = 0.71
决策: 中等 ROI → 生成 (法律要求证明了成本的合理性)
```

## 关键用户旅程定义

无论严格的 ROI 计算如何，都具有高优先级的测试：

### 强制覆盖区域

1.  **影响收入的流程**
    - 端到端的支付处理
    - 结账和订单完成
    - 订阅管理
    - 购买确认和收据

2.  **法律要求的流程**
    - GDPR 数据删除/导出
    - 用户同意管理
    - 数据保护合规性
    - 法规审计追踪

3.  **高频核心功能**
    - 用户认证/授权 (>80% 的用户)
    - 主要实体的核心 CRUD 操作
    - 关键业务工作流
    - 主要数据模型的数据完整性

**预算例外**：关键用户旅程在有明确理由的情况下可以超出标准预算限制。

## 测试选择指南

### 选择阈值

**集成测试**:
- ROI > 3.0: 强有力的候选
- ROI 1.5-3.0: 根据可用预算考虑
- ROI < 1.5: 跳过或转换为单元测试

**E2E 测试**:
- ROI > 2.0: 强有力的候选
- ROI 1.0-2.0: 如果是关键用户旅程则考虑
- ROI < 1.0: 跳过 (相对于价值而言过于昂贵)

### 下推分析

在生成更高级别的测试之前，询问：

1.  **这能用单元测试吗？**
    - 是 → 改为生成单元测试
    - 否 → 继续考虑集成测试

2.  **是否已被集成测试覆盖？**
    - 是 → 不创建 E2E 版本
    - 否 → 如果 ROI 合理，则考虑 E2E 测试

**示例**:
- "税收计算准确性" → 单元测试 (纯逻辑)
- "税款应用于订单总额" → 集成测试 (多个组件)
- "用户在结账流程中看到正确的税款" → 仅当是关键用户旅程时才进行 E2E 测试

## 重复数据删除策略

在生成任何测试之前：

1.  **搜索现有测试套件** 以查找类似的覆盖范围
2.  **检查不同测试级别的重叠场景**
3.  **识别已在别处覆盖的冗余验证**

**决策矩阵**:
```
找到现有覆盖范围了吗？
  → 完全覆盖: 跳过新测试
  → 部分覆盖: 扩展现有测试
  → 无覆盖: 生成新测试
```

## 在测试生成中的应用

### 阶段 1: 候选枚举
- 列出所有可能的测试场景
- 为每个候选分配 ROI 元数据

### 阶段 2: 基于 ROI 的选择
1. 计算每个候选的 ROI
2. 应用重复数据删除检查
3. 应用下推分析
4. 按 ROI 降序排序

### 阶段 3: 预算执行
- 在预算限制内选择前 N 个测试
- 记录预算使用情况
- 报告选择理由

**参见**：`.agents/tasks/acceptance-test-generation.md` 获取详细的实现过程

## 持续改进

### 需要跟踪的指标

1.  **选择率**: 生成的测试数 / 总候选数
    - 目标: 25-35% (表明有效的过滤)

2.  **平均 ROI**: 生成测试的平均 ROI
    - 目标: 集成测试 >3.0，E2E 测试 >1.5

3.  **预算利用率**: 实际测试数 / 预算限制
    - 目标: 80-100% (充分利用有价值的测试槽位)

4.  **缺陷检测率**: 捕获的 Bug 数 / 总测试数
    - 随时间跟踪以验证 ROI 预测

### 校准

定期审查：
- 高 ROI 的测试是否真的在捕获 Bug？
- 成本估算是否准确？
- 业务价值评级是否与利益相关者的优先级一致？

**根据经验数据调整公式权重**

## 要避免的反模式

❌ **操纵系统**:
- 夸大业务价值分数以证明偏爱的测试是合理的
- 当 ROI 与直觉相矛盾时忽略它
- 仅对偏好的测试进行选择性的 ROI 计算

✅ **正确用法**:
- 对所有候选一致地应用 ROI 计算
- 在覆盖 ROI 决策时记录理由
- 使用经验数据随时间校准分数

❌ **分析瘫痪**:
- 在精确的 ROI 计算上花费过多时间
- 争论分数的单点差异
- 将 ROI 视为精确科学而非决策辅助

✅ **实际应用**:
- 使用 ROI 进行相对优先级排序，而非绝对精确
- 关注数量级的差异 (8.9 vs 0.34)
- 对明显的高/低 ROI 案例做出快速决策
