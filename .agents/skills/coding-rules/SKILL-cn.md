# 开发规则

## 特定语言参考

对于特定语言的规则，也请阅读：
- **TypeScript**: [references/typescript.md](references/typescript.md)

## 基本原则

✅ **积极重构**
- 持续改进代码结构和可读性
- 以小而安全的步骤进行代码更改
- 优先考虑可维护性，而非初始实现速度

❌ **未使用的“以防万一”的代码** - YAGNI 原则
- 不要为假设的未来需求编写代码
- 立即删除未使用的函数、变量和导入
- 保持代码库精简，专注于当前需求

## 注释编写规则

- **功能描述焦点**：描述代码“做什么”，而不是“如何工作”
- **无历史信息**：不要在注释中记录开发历史
- **永不过时**：只写在任何时候阅读都有效的内容
- **简洁**：将解释保持在必要的最低限度
- **解释“为什么”**：注释应解释原因，而非实现细节

## 函数设计

**参数管理**
- **最多0-2个参数**：对于3个及以上的参数，使用结构化数据 (对象/结构体/字典)
  ```
  ✅ 好: createUser({name, email, role})
  ❌ 避免: createUser(name, email, role, department, startDate)
  ```
  *注意：使用你语言的惯用方法来组织参数*

**依赖注入**
- **显式注入外部依赖**：确保可测试性和模块化
- 将依赖作为参数传递 (函数、构造函数或其他适合语言的机制)
- 避免全局状态、直接实例化或隐式依赖
- 在适用时，优先使用接口/契约而非具体实现

## 错误处理

**绝对规则**：禁止错误抑制。所有错误必须有日志输出和适当的处理。

**分层错误处理**
- **表示层**: 将错误转换为用户友好的消息，记录日志时排除敏感信息
- **业务层**: 检测业务规则违规，传播特定于领域的错误
- **数据层**: 将技术错误转换为领域错误

**结构化日志记录和敏感信息保护**
绝不在日志中包含敏感信息：
- 密码、令牌、API 密钥、机密
- 信用卡号、个人识别号码
- 任何个人可识别信息 (PII)

**异步错误处理**
- 使用适合你语言的错误处理机制
- 始终记录并适当地传播错误
- 在适用时设置全局错误处理器

## 整洁代码原则

✅ **推荐实践**
- 立即删除未使用的代码
- 移除调试语句和临时日志
- 使用有意义的变量和函数名
- 保持函数小而专一

❌ **避免这些实践**
- 被注释掉的代码 (使用版本控制来查看历史)
- 没有解释的魔法数字
- 深度嵌套 (倾向于提早返回)
- 做多个不相关事情的函数

## 重构技巧

**基本策略**
- **小步快走**：通过逐步改进保持始终可工作的状态
- **安全更改**：一次最小化更改范围
- **行为保证**：在进行中确保现有行为保持不变

**实施步骤**
1. 理解现状
2. 进行渐进式更改
3. 验证行为
4. 最终验证

**优先级顺序**
1. 移除重复代码
2. 拆分大型函数
3. 简化复杂条件分支
4. 改进架构

## 性能考虑

**通用原则**
- 在优化前测量 (避免过早优化)
- 关注算法复杂度而非微观优化
- 考虑内存使用，尤其是在处理大型数据集时
- 为用例使用适当的数据结构

**资源管理**
- 正确关闭文件、连接和其他资源
- 注意长期运行应用程序中的内存泄漏
- 使用高效的算法进行数据处理

## 代码组织

**文件结构**
- 将相关功能组合在一起
- 分离关注点 (业务逻辑、数据访问、表示)
- 在整个项目中始终使用一致的命名约定
- 将配置与业务逻辑分开

**模块化**
- 编写小而专注的模块/函数
- 最小化模块间的依赖
- 在组件间使用清晰的接口
- 遵循单一职责原则
