## 文档创建前的强制流程 [严格遵守]

**这些步骤必须完成才能通过入口关卡：**

### 1. 标准识别关卡 [必需 - 不可跳过]
必须在任何调查之前执行：

1.  **识别项目标准**
    - 扫描项目配置、规则文件和现有代码模式
    - 对每个标准进行分类：**显式** (已记录) 或 **隐式** (仅观察到的模式)

2.  **在设计文档中记录**
    - 在“适用标准”部分列出，并附上 `[explicit]` / `[implicit]` 标签
    - 隐式标准在设计继续前需要用户确认

3.  **对齐规则**
    - 设计决策必须引用适用的标准
    - 偏离需要有记录的理由

### 2. 现有文档调查 [必需 - 不可跳过]
必须在任何设计之前执行：

1.  **PRD 调查** (如适用)
    - 在 `docs/prd/` 目录中检查相关的 PRD
    - 审查需求和成功标准
    - 注意任何已定义的约束或范围边界
    - 在设计文档头部包含 PRD 引用

2.  **相关设计文档搜索**
    - 在 `docs/design/` 目录中搜索现有设计
    - 识别相似或依赖的功能
    - 审查使用的架构模式
    - 注意集成点和数据流

3.  **现有 ADR 审查**
    - 在 `docs/adr/` 目录中搜索 ADR
    - 识别相关的技术决策
    - 检查可能需要更新的被取代的 ADR
    - 在“先决 ADR”部分列出适用的 ADR

### 3. 现有代码调查 [必需 - 不可跳过]
必须在文档审查后执行：

1.  **实现文件路径验证**
    - 首先掌握整体项目结构
    - 然后通过搜索相关组件/模块名称来识别目标文件
    - 记录并区分现有的实现位置和计划的新位置

2.  **现有 API 调查** (仅当更改现有功能时)
    - 列出目标组件的主要公共操作
    - 通过搜索组件使用模式来识别调用点

3.  **相似功能搜索** (防止 `ai-development-guide.md` 中的模式5)
    - 在现有代码中搜索与计划功能相关的关键字
    - 寻找具有相同领域、职责或配置模式的实现
    - 决策与行动：
        - 找到相似功能 → 使用该实现 (不创建新的)
        - 相似功能是技术债务 → 创建 ADR 改进提案
        - 没有相似功能 → 继续进行新实现

4.  **在设计文档中包含**
    - 始终在 "## 现有代码库分析" 部分包含调查结果
    - 清晰记录相似功能的搜索结果
    - 记录采纳的决策和理由

5.  **代码检查证据**
    - 在设计文档的 "代码检查证据" 部分记录所有检查过的文件和关键函数
    - 每个条目必须说明其相关性 (相似功能 / 集成点 / 模式参考)

### 4. 数据表示决策 [适用时必需]
当设计引入或显著修改数据结构时：

1.  **重用 vs 新建评估**
    - 搜索具有重叠目的的现有结构
    - 评估：语义契合度、职责契合度、生命周期契合度、边界/互操作成本

2.  **决策规则**
    - 所有标准都满足 → 重用现有的
    - 1-2个标准失败 → 评估使用适配器进行扩展
    - 3个以上标准失败 → 有理由创建新结构
    - 在设计文档中记录决策和理由

### 5. 协议清单【最重要】
必须在设计文档创建之初执行：

1.  **用要点列出与用户的协议**
    - 范围 (要更改什么)
    - 非范围 (不更改什么)
    - 约束 (兼容性要求等)
    - 性能要求

2.  **确认在设计中的体现**
    - [ ] 指明每个协议在何处体现
    - [ ] 确认没有设计与协议相矛盾
    - [ ] 如果有任何协议未体现，说明原因

### 6. 最新信息研究 [阻塞性要求]

**网络研究必须使用 `SESSION_BASELINE_DATE` 的年份 - 绝不硬编码年份：**
- 格式："[技术] 最佳实践 [来自 SESSION_BASELINE_DATE 的年份]"
- 必需于：引入新技术/库，安全实现
- 验证：截至 `SESSION_BASELINE_DATE` 的最新版本、重大变更、安全更新

**搜索示例**：`[技术] 最佳实践 [年份]`，`[框架] 官方文档`

## ADR 创建指南

### ADR 取代流程 [对于相关 ADR 是强制性的]

当创建的 ADR 替换或修改了先前的决策时：

1.  **识别相关的 ADR**
    - 搜索覆盖相同领域/技术的 ADR
    - 检查会被新决策所矛盾的 ADR
    - 列出所有需要被取代的 ADR

2.  **更新现有 ADR 状态**
    - 更改旧 ADR 的状态：`状态: 被 ADR-XXXX 取代`
    - 添加取代说明，包括日期和新的 ADR 引用
    - **不要** 删除旧的 ADR - 保持历史记录

3.  **在新 ADR 中引用**
    - 在头部添加 "取代: ADR-YYYY"
    - 解释改变了什么以及为什么
    - 保持决策演变的可追溯性

## 验收标准创建指南

**原则**：具体、可验证的条件，可转化为测试用例
**好的**："使用正确凭据认证后，导航到仪表板"
**不好的**："登录功能正常"

### EARS 格式 [推荐]

使用 EARS 关键字来标准化 AC 结构：

| 关键字 | 测试类型 | 示例 |
|---------|-----------|---------|
| **When (当)** | 事件触发 | "**当** 用户点击提交时，系统应保存表单" |
| **While (在...期间)** | 基于状态 | "**在** 登录期间，系统应显示用户名" |
| **If-then (如果-则)** | 条件性 | "**如果** 购物车为空，**则** 显示空消息" |
| (无) | 始终为真 | "系统应加密所有密码" |

### 行为优先原则 [关键]

**核心原则**：AC = 可在隔离的 CI 环境中验证的用户可观察行为

**在编写任何 AC 之前，应用3个强制性检查：**

#### 1. 用户可观察性检查
**问题**："用户（或系统操作员）能观察到这个行为吗？"
- **如果否** → 这是 **实现细节**，从 AC 中排除
- **如果是** → 继续检查 2

**示例**：
- ❌ 不好 (实现细节): "密码必须使用 bcrypt 加盐10轮进行哈希"
- ✅ 好 (用户可观察): "在登录尝试失败后，用户将被锁定15分钟"

#### 2. 验证上下文检查
**问题**："这可以在没有完整系统集成的情况下进行验证吗？"
- **如果是** → 这是 **单元/组件级别**，从集成/E2E AC 中排除
- **如果否** → 这是集成/E2E 测试的有效 AC，继续检查 3

**示例**：
- ❌ 不好 (单元级别): "`calculateTax` 函数为给定输入返回正确的值"
- ✅ 好 (集成级别): "结账后，订单总额包含正确的税额"

#### 3. CI 环境检查
**问题**："这能在 CI 中确定性地验证吗？"
- **如果否** → 排除 (例如，性能指标，真实的外部服务)
- **如果是** → 有效 AC

**示例**：
- ❌ 不好 (不确定性): "API 响应时间必须 < 200ms"
- ✅ 好 (确定性): "系统处理结账请求时不阻塞用户交互"

**增强的包含/排除标准**：

**包含 (高自动化投资回报率)**：
- 业务逻辑正确性 (计算，状态转换)
- 数据完整性和持久性行为
- 用户可见功能的完整性
- 错误处理行为 (用户看到/体验到的)

**排除 (低自动化投资回报率)**：
- 真实的外部服务连接 → 使用契约/接口验证代替
- 性能指标 → 在 CI 中不确定，使用专门的性能测试
- 实现细节 (哈希算法，内部函数调用) → 关注可观察行为
- UI 布局细节 → 关注信息可用性，而非像素级完美渲染

## 要避免的反模式

**ADR 反模式**
推荐：评估3个以上选项，并提供有研究支持的权衡
原因：单一选项的决策缺乏验证；没有缺点的选项是不现实的

**设计反模式**
推荐：具体、可测试的验收标准，并进行影响分析
原因：模糊的标准无法验证；缺少影响分析会导致集成问题
