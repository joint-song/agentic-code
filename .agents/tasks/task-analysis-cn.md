# 任务分析

## 必要 skills [强制性 - 必须激活]

**skill 可用性验证：**
1. [验证激活状态] .agents/skills/metacognition/SKILL.md (会话开始时加载)
2. [如果未激活则加载] .agents/context-maps/task-skills-matrix-cn.yaml

**加载协议：**
- 步骤 1: 验证 `metacognition.md` 自初始会话设置起即为激活状态
- 步骤 2: 检查 `task-skills-matrix-cn.yaml` 在工作内存中是否为激活状态
- 步骤 3: 如果 `task-skills-matrix-cn.yaml` 未激活 → 执行 **阻塞性读取 (BLOCKING READ)**
- 步骤 4: 在进行任务分析前 **确认** 所有 skills 都已激活

**所需证据：**
```
skill 状态验证：
✓ metacognition.md - 激活 (来自会话设置)
✓ task-skills-matrix-cn.yaml - 激活 (已加载/已验证)
```

## 目的

确定任务类型、规模和所需资源。

## 使用时机

- 在任何用户请求开始时
- 当任务范围不明确时
- 当切换到不同类型的工作时

## 完成条件

□ 已识别任务类型 (实现/研究/设计/文档/调试/审查/其他)
□ 已确定任务规模：
  - 小规模：影响1-2个文件
  - 中等规模：影响3-5个文件
  - 大规模：影响6个及以上文件
□ 已识别所需资源：
  - 需要的 skills
  - 外部依赖
  - 要参考的现有代码
□ 已定义成功标准 (可衡量的)
□ 已记录约束和假设

## 强制执行顺序 [要求严格遵守]

### 步骤 0: 初始设置 [阻塞性 - 不可跳过]
如果 `SESSION_BASELINE_DATE` 尚未建立：
1. [立即] 执行 `date` 命令
2. [存储] 结果为 `SESSION_BASELINE_DATE`，供 **整个** 会话使用
3. [强制] **所有** "当前/最新/近期" 的引用 **必须** 使用 `SESSION_BASELINE_DATE` 的年份

**违规示例**：当 `SESSION_BASELINE_DATE` 显示为 "2025" 时，在网络研究中使用 "2024" = **严重错误**

### 步骤 1: 理解请求本质

- 用户试图实现什么？
- 这是一个表象还是真正的目标？
- 以前做过哪些类似的任务？

### 步骤 2: 分类任务类型 [必需]

**实现**：创建或修改代码
- 新功能
- Bug 修复
- 重构
- 性能优化

**研究**：信息收集
- 代码探索
- 架构分析
- 可行性研究

**设计**：规划和文档
- 技术规格
- 架构决策
- API 设计

**文档**：编写文档
- README 更新
- API 文档
- 用户指南

**调试**：问题解决
- 错误调查
- 性能分析
- 行为诊断

**审查**：评估和验证
- 技术文档审查 (设计文档, ADR)
- 代码审查
- 测试审查 (集成/E2E 测试)

### 步骤 3: 估算规模 [必需]

计算受影响的组件：
- 要创建/修改的文件数量
- 涉及的系统/模块数量
- 集成复杂度
- 测试要求

#### 文件数量估算流程 [强制性]

在确定规模之前，通过具体步骤调查现有代码：

1.  **识别入口点**：找到与任务直接相关的文体 (例如，组件、API 端点、处理器)
2.  **追踪依赖**：跟随导入和调用者发现相关联的文件
3.  **包含测试文件**：将相关的测试文件计入总数
4.  **明确列出**：记录受影响的文件路径作为规模确定的证据

**规模确定必须引用具体的文件路径作为证据。**

示例输出：
```
受影响的文件 (5个文件 → 中等规模):
- src/components/UserProfile.tsx (修改)
- src/hooks/useUser.ts (修改)
- src/api/userApi.ts (修改)
- src/components/__tests__/UserProfile.test.tsx (修改)
- src/hooks/__tests__/useUser.test.ts (修改)
```

#### 规模置信度

指明规模确定的确定性级别：

- **confirmed (已确认)**：基于明确的需求和已识别的文件，规模是确定的
- **provisional (临时的)**：规模可能会根据用户对澄清问题的回答而改变

当为临时时，始终记录 **范围依赖项** - 那些答案会影响规模的问题。

#### 范围依赖项

当规模置信度为临时时，明确记录可能改变规模的因素：

```
范围依赖项:
- 认证方法: 使用现有的 OAuth → 中等 (3个文件) / 新实现 → 大规模 (8个文件)
- 缓存要求: 无 → 中等 / 需要 → 大规模 (增加 Redis 集成)
```

这使得：
1.  用户能够理解哪些决策会影响范围
2.  在需求澄清后重新评估
3.  规模确定的理由透明化

### 步骤 4: 执行 skill 选择 [阻塞性检查点]

**执行关卡 - 任何步骤跳过则系统暂停：**
1. [阻塞性读取] 来自 `.agents/context-maps/` 的 `task-skills-matrix.yaml`
2. [强制匹配] 任务类型 + 规模与矩阵进行匹配
3. [分类输出]:
   - 必要 skills：**立即进行阻塞性读取**
   - 推荐 skills：评估上下文，然后如果适用则进行 **阻塞性读取**
   - 条件 skills：检查条件，如果满足则进行 **阻塞性读取**
4. [验证关卡] 在所有必要 skills 加载前 **不能继续**
5. [合规证明] 输出必须列出：
   ```
   skill 成功加载：
   ✓ [文件路径] - [加载原因]
   ✓ [文件路径] - [应用于哪个方面]
   ```
6. [任务跟踪] **立即** 将所有识别出的 **阻塞性读取** 添加到你的内部任务管理（任务列表）中：
   ```
   [来自 task-analysis 的阻塞性读取 - skill 选择]
   已添加到任务列表：
   ✓ [文件路径] - 必要 skill
   ✓ [文件路径] - 条件 skill (条件已满足)
   ```

### 步骤 5: 识别额外资源

确定需要什么：
- 哪些 skill 文件适用
- 外部库/工具
- 参考实现
- 文档来源

### 步骤 6: 定义成功标准

- 特定功能正常工作
- 测试通过
- 性能指标满足
- 文档完成

### 步骤 7: 工作流推荐

基于规模和复杂性：
- **小规模 (1-2个文件)**：直接执行任务，不需要工作流
- **中/大规模 (3+个文件)**：**推荐** `agentic-coding.md` 工作流
  - 提问："此任务将受益于带有设计文档和工作计划的结构化工作流。是否继续？[Y/n]"
  - 如果 **是**：加载并遵循 `agentic-coding.md`
  - 如果 **否**：直接执行单个任务定义

### 步骤 8: 强制性任务跟踪 [阻塞性 - 自动执行]

**对于所有有阻塞性读取要求的任务：**

1.  **[扫描阻塞性读取]** 识别所有需要 **阻塞性读取** 的文件：
    - 从选定的工作流 (如果是中/大规模)
    - 从将要执行的任务定义
    - 从将要加载的 skills

2.  **[添加到任务列表]** 将所有识别出的 **阻塞性读取** 添加到你的内部任务管理（任务列表）中：
   ```
   任务列表 - 阻塞性读取：
   □ 阻塞性读取: [文件路径] - [原因/阶段]
   □ 阻塞性读取: [文件路径] - [原因/阶段]
   □ 每次阻塞性读取后进行 skill 状态验证
   ```

3.  **[需要证据]** 显示任务跟踪确认：
   ```
   [任务跟踪完成]
   从以下来源识别出阻塞性读取：
   ✓ 工作流阶段: [文件列表]
   ✓ 任务定义: [文件列表]
   ✓ 必要 skills: [文件列表]

   已添加到任务列表：
   ✓ 阻塞性读取总数: [数量]
   ✓ 验证关卡: [数量]
   ```

4.  **[强制执行]** 在以下条件满足前 **不能** 继续：
    - **所有** 阻塞性读取都已识别并添加到任务列表
    - 上述任务跟踪证据已显示
    - 每个 **阻塞性读取** 都作为任务列表中的一个明确项目

**违规处理：**
- 任务列表中缺少任何 **阻塞性读取** = **立即暂停**
- 执行期间跳过任何 **阻塞性读取** = **严重错误**
- 未经验证就继续 = **返回任务分析**

## 可交付成果

- 任务分类输出
- 路径推荐

## 常见模式

### 功能请求
1. 识别核心功能
2. 估算组件变更
3. 考虑边缘案例
4. 规划测试方法

### Bug 修复
1. 理解预期与实际行为
2. 识别受影响的组件
3. 确定根本原因分析方法
4. 规划验证方法

### 重构
1. 识别改进目标
2. 评估当前结构
3. 估算变更范围
4. 规划增量方法

### 审查
1. 识别审查目标 (文档/代码/测试)
2. 加载适当的审查任务定义
3. 应用任务定义中的审查标准
4. 记录发现和建议

## 决策树

**与代码相关？**
- 是 → 创建新代码？
  - 是：实现任务
  - 否 → 修复问题？
    - 是：调试任务
    - 否：重构任务
- 否 → 评估现有工作？
  - 是：审查任务 → 确定目标：
    - 文档 (设计/ADR) → `technical-document-review`
    - 代码 → `code-review`
    - 测试 → `integration-test-review`
  - 否 → 信息收集？
    - 是：研究任务
    - 否 → 规划？
      - 是：设计任务
      - 否：文档任务
