## 执行指南

### 1. 计划结构

创建工作计划文档，包含：
- **概述**：正在构建/更改的内容
- **阶段**：工作的逻辑分组
- **任务**：独立的实现单元
- **依赖关系**：什么必须在什么之前完成
- **风险**：潜在问题和缓解措施
- **测试参考**：链接到生成的测试骨架 (如果可用)

### 2. 任务分解原则 [单一提交规则]

**强制粒度 - 1个任务 = 1次提交**：
- 每个任务 **必须** 代表一个原子性变更
- 每个任务 **必须** 可以独立提交
- 每个任务在完成后 **必须不** 破坏构建

**文件数量指南**：
- **理想**：每个任务1-2个文件 (一次集中的更改)
- **最多**：每个任务3个文件 (如果紧密耦合)
- **禁止**：4个及以上文件 (**必须** 拆分成更小的任务)

**独立性要求**：
- 可独立验证 (有自己的测试/验证)
- 回滚安全 (可以回滚而不破坏)
- 自包含 (不会使系统处于部分状态)

**复选框更新协议 [强制性]**：
- **开始任务前**：验证复选框存在 `- [ ]`
- **完成任务后**：将复选框更新为 `- [x]` (标准 Markdown)
- **强制执行**：已完成任务未勾选 = 违反协议
- **参考**：在实现可测试功能时，链接到相关的测试骨架

### 3. 任务格式 [强制模板]

```markdown
## 任务 N: [任务名称]

### 入口条件
- [ ] 前置依赖已完成
- [ ] 理解要构建的内容
- [ ] 准备好遵循 TDD

### 范围 [最多2个文件，否则拆分]
- 影响文件: [确切的文件路径]
- 组件: [具体的名称]

### 实现步骤 (TDD + 提交)
1.  红 (RED): 编写失败的测试
2.  绿 (GREEN): 编写使测试通过的代码
3.  重构 (REFACTOR): 改进代码
4.  验证 (VERIFY): 运行质量检查 (要求0错误)
5.  提交 (COMMIT): Git 提交 (遵循单一提交原则: 1个任务 = 1次提交)

### 退出条件
- [ ] 测试通过
- [ ] 质量检查以0错误通过 (根据 `testing/SKILL.md` 标准)
- [ ] 更改已提交到 git
- [ ] 工作计划文档中的任务复选框已标记为 [x]

### 依赖关系
- 依赖于: 任务 [X]
- 阻塞: 任务 [Y]
```

### 4. 排序策略

1.  **基础先行**：核心结构优于功能
2.  **尊重依赖**：先决条件优于依赖项
3.  **保持可测试性**：每一步都可验证
4.  **风险前置**：尽早处理复杂/不确定的部分

### 5. 常见模式

**功能实现**
```
阶段 1: 数据层
- 任务 1: 定义数据模型
- 任务 2: 创建存储库

阶段 2: 业务逻辑
- 任务 3: 实现服务
- 任务 4: 添加验证

阶段 3: 接口
- 任务 5: 创建 API 端点
- 任务 6: 添加错误处理

阶段 4: 测试
- 任务 7: 单元测试
- 任务 8: 集成测试
```

**重构**
```
阶段 1: 准备
- 任务 1: 为当前行为添加测试
- 任务 2: 创建抽象层

阶段 2: 迁移
- 任务 3: 实现新结构
- 任务 4: 逐个组件迁移

阶段 3: 清理
- 任务 5: 移除旧代码
- 任务 6: 更新文档
```

## 可交付成果

位于 `docs/plans/YYYYMMDD-{type}-{description}.md` 的工作计划文档，包含：
- 遵循单一提交原则的任务分解
- 带有依赖关系的执行顺序
- 用于进度跟踪的复选框 (`- [ ]` 格式)
- 每个任务的验证方法
- 风险缓解策略

**关键**：工作计划位置 **必须** 在 `docs/plans/` 目录中

## 质量标准

任务 **必须** 是：
- **原子性**：一次提交的变更量
- **可跟踪**：有用于进度的复选框
- **可衡量**：明确的完成标准
- **可测试**：定义了验证方法
- **有序的**：明确说明了依赖关系
- **大小适中**：1-2个文件 (最多3个)

**强制执行检查清单**：
☐ 每个任务都可以是一次提交
☐ 每个任务都有 `- [ ]` 复选框
☐ 每个任务都有验证命令
☐ 没有任务超过3个文件
☐ 依赖关系已清晰标记

## 反模式

避免：
- 模糊的任务 ("提升性能")
- 巨大的任务 (10+ 个文件)
- 循环依赖
- 缺少验证方法
- 不明确的完成标准
