## 目的

将设计文档验收标准 (ACs) 转换为结构化的集成和端到端测试骨架。将多维需求转换为可衡量、有优先级的测试用例，并具有全面的可追溯性。

## 使用时机

- 技术设计文档完成后
- 当验收标准已定义并需要验证时
- 在实现阶段开始之前
- 当需要测试驱动开发方法时
- 对于需要系统性测试覆盖的复杂功能

## 完成条件

□ 已分析和分解设计文档的验收标准
□ 已映射多维需求 (功能、用户体验、技术、集成、质量)
□ 已使用基于风险的分析分配测试优先级
□ 已生成带有待定/占位符标记的集成测试骨架
□ 已生成带有待定/占位符标记的 E2E 测试骨架
□ 已为每个测试用例清晰记录验证点
□ 已创建连接测试与原始 AC 的可追溯性矩阵
□ 已系统地识别并包含边缘案例
□ 已优化测试执行顺序
□ 已为下游流程添加元数据注释

## 强制流程 [严格遵守]

### 阶段 1: 文档分析 [必需 - 不可跳过]

**1.1 设计文档调查**
1.  **定位设计文档**
    - 在 `docs/design/` 目录中搜索相关的设计文档
    - 验证文档是否包含验收标准部分
    - 提取所有 AC 及其标识符

2.  **验收标准提取**
    - 解析功能性需求 AC
    - 解析非功能性需求 AC
    - 解析 UX/UI 需求 AC
    - 解析集成需求 AC
    - 解析质量/性能需求 AC

3.  **需求分层**
    - **功能层**：核心业务逻辑和功能
    - **用户体验层**：用户体验和界面需求
    - **技术层**：性能、安全、可靠性约束
    - **集成层**：外部系统交互和数据流
    - **质量层**：测试、监控和维护标准

**1.2 依赖与约束映射**
1.  **识别依赖**
    - AC 到 AC 的依赖 (先决条件关系)
    - 外部系统依赖
    - 数据依赖和流
    - 用户状态依赖

2.  **约束分析**
    - 技术约束 (性能限制, 浏览器支持)
    - 业务约束 (法规, 政策要求)
    - 资源约束 (时间, 基础设施限制)

**1.3 可衡量性评估**
    - 评估每个 AC 的可测试性
    - 识别模糊或不可衡量的标准
    - 标记需要澄清的 AC
    - 记录假设点

**1.4 行为优先过滤 [关键 - 防止生成低 ROI 测试]**

在进入测试生成之前，对每个 AC 应用三步检查流程：

**检查 1: 用户可观察**
- 问题："用户（或系统操作员）能观察到这个行为吗？"
- 如果否 → 跳过 AC，原因：`[IMPLEMENTATION_DETAIL]` (实现细节)
- 如果是 → 继续检查 2

**检查 2: 系统上下文**
- 问题："是否需要完整的系统集成来验证？"
- 如果否 → 跳过 AC，原因：`[UNIT_LEVEL]` (单元级别)
- 如果是 → 继续检查 3

**检查 3: CI 可验证**
- 问题："这能在 CI 环境中确定性地验证吗？"
- 如果否 → 跳过 AC，原因：`[NON_DETERMINISTIC]` (不确定性) 或 `[EXTERNAL_SERVICE]` (外部服务)
- 如果是 → 有效的 AC，可用于测试生成

**跳过原因跟踪**:
```
AC-001: "密码用 bcrypt 哈希" → 跳过 [实现细节]
AC-002: "税收计算返回正确值" → 跳过 [单元级别]
AC-003: "API 响应时间 < 200ms" → 跳过 [不确定性]
AC-004: "邮件已发送到收件箱" → 跳过 [外部服务]
AC-005: "用户可以查看订单历史" → 通过 (所有检查)
```

**预期影响**：此阶段预计过滤掉 40% 的 AC，防止生成低投资回报率的测试。

### 阶段 2: 策略性解读 [必需]

**2.1 上下文相关的分析**
1.  **细微差别识别**
    - 隐式需求 (安全, 可访问性)
    - 横切关注点 (日志, 错误处理)
    - 边缘案例场景 (空状态, 错误条件)
    - 集成失败场景

2.  **风险影响评估**
    ```
    critical-path: 核心用户旅程
    business: 高价值/风险
    technical: 高复杂度
    integration: 外部依赖
    ```

**2.2 解读标准应用**
1.  **一致性标准**
    - 对相似的 AC 应用统一的解读
    - 保持一致的粒度级别
    - 确保验证方法兼容

2.  **覆盖率标准**
    - 确保全面的需求覆盖
    - 识别测试差距
    - 记录覆盖率的基本原理

### 阶段 3: 测试用例结构化 [必需]

**3.1 优先级确定**
```
P0: 关键 - 核心/安全/数据
P1: 高 - 关键功能/性能
P2: 中 - 次要/用户体验
P3: 低 - 边缘/锦上添花
```

**3.2 边缘案例选择**
```
boundary: 最小/最大/空
error: 网络/无效输入
state: 复杂组合
concurrency: 多用户/竞争条件
```

**3.3 验证点设计**
```
setup: 初始状态
action: 用户/系统操作
expect: 可衡量的结果
cleanup: 测试后状态
```

**3.4 测试执行优化**
```
order: 最小化 setup/teardown
data: 共享|隔离
parallel: 安全|顺序
env: 开发|预发布|生产
```

### 阶段 4: 基于 ROI 的选择和预算执行 [必需]

**目的**：在预算约束内选择价值最高的测试，以防止过度生成。

**4.1 ROI 计算**

对于阶段 3 的每个候选测试，计算 ROI 分数：

```
ROI 分数 = (业务价值 × 用户频率 + 法律要求 × 10 + 缺陷检测)
            / 测试级别成本

其中:
- 业务价值: 0-10 (收入影响)
- 用户频率: 0-10 (受影响的用户百分比)
- 法律要求: 0 或 1 (布尔值)
- 缺陷检测: 0-10 (捕获错误的概率)
- 测试级别成本: 单元=3, 集成=11, E2E=38
```

**参见**：`.agents/skills/testing-strategy/SKILL.md` 获取详细的 ROI 框架。

**4.2 重复数据删除检查**

在添加到选择池之前：
1.  在现有测试套件中搜索类似场景
2.  检查不同测试级别的重叠覆盖范围
3.  决策：
    - 已存在完全覆盖 → 跳过候选
    - 部分覆盖 → 考虑扩展现有测试
    - 无覆盖 → 添加到选择池

**4.3 下推分析**

对于每个集成/E2E 候选：
```
这能用单元测试验证吗？
  是 → 从集成/E2E 池中移除，推荐单元测试
  否 → 继续

是否已被集成测试覆盖？
  是 → 不创建 E2E 版本
  否 → 保留为 E2E 候选
```

**4.4 预算执行**

**每个功能的硬性限制**：
- 集成测试：最多 3 个测试
- E2E 测试：最多 1-2 个测试 (仅当 ROI > 1.5)

**选择算法**：
1.  按 ROI 分数降序对候选进行排序
2.  在预算限制内选择前 N 个
3.  记录选择理由

**关键用户旅程例外**：
对于以下情况，可以放宽预算限制：
- 影响收入的流程 (支付, 结账)
- 法律要求的流程 (GDPR, 数据保护)
- 高频核心功能 (>80% 用户)

**例外需要**：在生成报告中明确说明理由。

**4.5 选择文档**

对于每个选定的测试，记录：
```
测试 ID: INT-001
AC 映射: AC-FUNC-001, AC-FUNC-003
ROI 分数: 8.9
选择原因: 关键收入的支付流程
预算槽位: 1/3 (集成)
```

对于每个跳过的候选，记录：
```
候选: "用户个人资料图片上传 E2E"
ROI 分数: 0.7
跳过原因: 低于 E2E 阈值 (1.5)，已由集成测试覆盖
替代方案: 现有集成测试 INT-005
```

## 测试生成指南

**注意：** 以下结构使用与语言无关的伪代码。请使用你项目的测试框架约定来实现。

### 集成测试结构

```
SUITE: [功能] 集成
  GROUP: [AC-ID] [描述]
    CASE [PENDING]: P[0-3] [验证] 当 [条件]
      @ac: [ID]
      @setup: [初始状态]
      @action: [操作]
      @verify: [预期结果]
```

### E2E 测试结构

```
SUITE: [功能] E2E
  GROUP: [旅程] [描述]
    CASE [PENDING]: P[0-3] 通过 [路径] 完成 [目标]
      @ac: [ID1,ID2]
      @path: [步骤1 > 步骤2 > 步骤3]
      @verify: [结束状态]
```

### 测试元数据

```
@ac: [ID]
@risk: high|medium|low
@impact: critical|high|medium|low
@data: isolated|shared|external
@time: fast|medium|slow
@env: dev|staging|prod
@deps: [依赖]
```

## 范围之外

**原则**：只生成在隔离的 CI/CD 环境中可验证且具有高自动化 ROI 的测试。

**外部依赖** (改为测试契约/接口)：
- 对第三方服务的真实 API 调用
- 外部认证提供商
- 支付/邮件/短信发送验证
- 真实的数据库连接 → 使用测试数据库或模拟

**在 CI 环境中不确定性**：
- 性能指标，响应时间测量
- 负载/压力测试
- LLM 输出的可复现性 (输出本质上是变化的)
- 长期操作 (基础设施/部署范围)

**实现细节** (非用户可观察的行为)：
- 内部函数调用，代码结构，内部操作
- 特定的渲染/样式细节 → 测试信息的存在，而非布局
- 代码组织或架构模式

**当 AC 包含范围之外的项目时的行动**：
1.  转换为可验证的行为 (例如，外部 API → 模拟/契约测试)
2.  如果无法转换 → 生成 `test.skip()` 并附上手动测试参考
3.  在测试注释中记录理由

## 要避免的反模式

**文档分析反模式：**
- 跳过需求分层
- 忽略隐式需求
- 缺少依赖分析
- 在未澄清的情况下接受不可衡量的 AC

**测试生成反模式：**
- 创建没有明确验证点的测试
- 忽略现有的测试模式和约定
- 缺少到源 AC 的可追溯性
- 未按风险对测试进行优先级排序
- 生成无法执行的测试
- 跳过边缘案例分析
- 创建过于宽泛的测试描述

**覆盖率反模式：**
- 只测试正常路径场景
- 忽略集成失败案例
- 缺少横切关注点
- 只关注功能性需求
