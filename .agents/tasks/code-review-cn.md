# 代码审查

## 必要 skills [强制性 - 必须激活]

**skill 可用性验证：**
1. [如果未激活则加载] `.agents/skills/coding-rules/SKILL.md`
2. [如果未激活则加载] `.agents/skills/ai-development-guide/SKILL.md`

**加载协议：**
- 步骤 1: 检查 `.agents/skills/coding-rules/SKILL.md` 在工作内存中是否为激活状态
- 步骤 2: 如果未激活 → 执行 **阻塞性读取 (BLOCKING READ)**
- 步骤 3: 检查 `.agents/skills/ai-development-guide/SKILL.md` 在工作内存中是否为激活状态
- 步骤 4: 如果未激活 → 执行 **阻塞性读取**
- 步骤 5: 在继续前 **确认** 所有必需的 skills 都已激活

## 目的

从第三方视角验证设计文档的合规性并评估实现的完整性。检测缺失的实现，验证验收标准，并提供质量报告。

## 使用时机

- 实现完成之后
- 审查代码变更时 (PR 审查，实现后审查)
- 验证设计文档合规性时

## 所需信息

- **implementationFiles**：要审查的文件列表 (必需)
- **designDocPath**：用于验证基准的设计文档路径 (可选 - 如果提供，则启用合规性验证)
- **workPlanPath**：用于验证已完成任务的工作计划路径 (可选)
- **reviewMode**：
  - `full`：完整验证 (默认)
  - `acceptance`：仅验收标准 (需要 designDocPath)
  - `architecture`：仅架构合规性 (需要 designDocPath)
  - `quality`：仅代码质量检查 (不需要 designDocPath)

## 完成条件

□ 所有实现文件已审查
□ 质量问题已记录并附有严重性
□ 已计算合规率 (如果提供了 designDocPath)
□ 已确定结论并附有理由
□ 已提供带优先级的行动项

## 审查流程

### 阶段 1: 加载基准文档 (如果提供了 designDocPath)

从设计文档中提取：
- 功能需求和验收标准
- 架构设计
- 数据流
- 错误处理策略

如果未提供 designDocPath，则跳至阶段 3 (代码质量检查)。

### 阶段 2: 实现验证 (如果提供了 designDocPath)

对每个实现文件进行验证：

| 检查项 | 验证内容 |
|------------|---------------------|
| AC 实现 | 验收标准有相应的代码 |
| 接口合规性 | 实现与设计文档的接口匹配 |
| 错误处理 | 错误场景已正确处理 |
| 测试存在性 | 功能存在测试用例 |

### 阶段 3: 代码质量检查 (始终执行)

| 指标 | 理想值 | 最大值 | 失败条件 |
|--------|-------|---------|-------------------|
| 函数长度 | <50 行 | 200 行 | 超过最大值 |
| 嵌套深度 | ≤3 层 | 4 层 | 超过最大值 |
| 单一职责 | 1个函数 = 1个目的 | - | 多重职责 |
| 错误处理 | 所有错误路径都已覆盖 | - | 缺少错误处理 |

### 阶段 4: 架构合规性 (如果提供了 designDocPath)

| 检查项 | 验证内容 |
|------------|---------------------|
| 设计匹配 | 实现与设计文档的架构匹配 |
| 数据流 | 数据流遵循设计 |
| 依赖关系 | 组件依赖关系正确 |
| 职责分离 | 职责已适当分离 |
| 重复检查 | 没有不必要的重复实现 (来自 `ai-development-guide.md` 的模式5) |

## 输出格式

### 状态确定

**pass (通过)** (90%+ 合规):
- 所有关键验收标准都已实现
- 没有高严重性的质量问题
- 架构合规性已验证

**needs_improvement (需要改进)** (70-89% 合规):
- 存在一些验收标准差距
- 存在中等严重性的质量问题
- 轻微的架构偏差

**needs_redesign (需要重新设计)** (<70% 合规):
- 缺少主要的验收标准
- 存在高严重性的质量问题
- 严重的架构违规

## 审查原则

1.  **保持客观性**
    - 独立于实现上下文进行评估
    - 以设计文档为唯一事实来源

2.  **建设性反馈**
    - 提供解决方案，而不仅仅是问题
    - 明确优先级

3.  **量化评估**
    - 尽可能量化
    - 消除主观判断

4.  **尊重实现**
    - 认可好的实现
    - 将改进作为可操作的项提出

## 上报标准

在以下情况时建议上报：
- 设计文档本身存在缺陷
- 发现安全问题
- 发现关键性能问题
- 实现与设计严重偏离

## 特殊考虑

### 对于原型/MVP
- 优先考虑功能而非完整性
- 考虑未来的可扩展性

### 对于重构
- 保持现有功能是最高优先级
- 量化改进程度

### 对于紧急修复
- 验证最小实现是否解决了问题
- 检查技术债务文档

## 要避免的反模式

- 批准不满足验收标准的代码
- 忽略架构违规
- 忽视缺失的错误处理
- 接受没有相应测试的代码
- 提供没有具体解决方案的模糊反馈
