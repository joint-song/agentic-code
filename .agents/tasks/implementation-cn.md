## TDD 实现流程

### 每次代码变更都遵循：

**1. 红 (RED) 阶段 - 首先编写失败的测试**
   - 在测试中定义预期行为
   - 运行测试以确认其失败
   - 此时不编写任何实现代码

**2. 绿 (GREEN) 阶段 - 使测试通过**
   - 编写最少的代码以使测试通过
   - 只专注于让测试变绿
   - 运行测试以确认其通过

**3. 重构 (REFACTOR) 阶段 - 改进代码**
   - 清理实现
   - 应用 `coding-rules/SKILL.md` 中的编码标准
   - 确保测试仍然通过

**4. 验证 (VERIFY) 阶段 - 质量检查**
   - 执行 `testing/SKILL.md` 质量检查命令部分的所有命令
   - 确认 **所有** 检查都以0错误通过
   - 准备提交

**5. 提交 (COMMIT) 阶段 - 版本控制 [强制性]**
   - 暂存当前实现的更改
   - 创建带有描述性消息的提交
   - 提交消息格式："feat: [实现了什么]" 或如果可用，则遵循工作计划任务名称
   - **强制执行**：在提交之前，实现任务 **未** 完成
   - **注意**：如果用户明确表示“不要提交”，则跳过此步骤

## TDD 的常见模式

**新功能**
1. 为新行为编写测试 (红)
2. 实现最小解决方案 (绿)
3. 重构并添加边缘案例 (重构)
4. 验证质量 (验证)

**Bug 修复**
1. 编写重现 Bug 的测试 (红)
2. 修复 Bug (绿)
3. 确保没有回归 (重构)
4. 验证质量 (验证)

**重构**
1. 确保测试存在并通过
2. 进行小幅更改
3. 每次更改后运行测试
4. 保持行为

### 5. 语言无关标准

无论何种语言：
- 清晰的变量名
- 一致的格式
- 正确的缩进
- 合理的文件组织
- 关注点分离

始终：
- 验证所有输入

- 使用参数化查询
- 避免硬编码密钥
- 遵循最小权限原则

## 要避免的反模式

1. **上帝函数 (God functions)**：在一个函数中做太多事
2. **魔法数字 (Magic numbers)**：使用命名常量
3. **深度嵌套**: 最多3层缩进
4. **忽略错误**: 始终处理或传播
5. **过早优化**: 先让它工作，然后再优化
6. **复制粘贴编码**: 提取通用代码
7. **不清晰的命名**: 要明确，不要耍小聪明
