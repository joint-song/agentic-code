# 文档审查

## 必要 skills [强制性 - 必须激活]

**skill 可用性验证：**
1. [如果未激活则加载] `.agents/skills/documentation-criteria/SKILL.md`
2. [条件性加载] `.agents/skills/testing-strategy/SKILL.md` (如果审查的是包含测试策略的设计文档)

**加载协议：**
- 步骤 1: 检查 `documentation-criteria/SKILL.md` 在工作内存中是否为激活状态
- 步骤 2: 如果 `documentation-criteria/SKILL.md` 未激活 → 执行 **阻塞性读取 (BLOCKING READ)**
- 步骤 3: 评估是否需要 `testing-strategy/SKILL.md` (包含测试策略部分的设计文档)
- 步骤 4: 如果需要且未激活 → 执行 **阻塞性读取**
- 步骤 5: 在继续前 **确认** 所有必需的 skills 都已激活

## 目的

审查技术文档（设计文档、ADR、PRD）的完整性、一致性和质量。识别差距，验证结构合规性，并评估故障场景的覆盖范围。

## 使用时机

- 审查现有的设计文档时
- 批准技术决策之前
- 从第三方角度评估文档质量时

## 所需信息

- **documentPath**：要审查的文档路径 (必需)
- **documentType**：文档类型 (必需)
  - `design-doc`：技术设计文档
  - `adr`：架构决策记录
  - `prd`：产品需求文档
- **templatePath**：用于验证基线的模板路径 (可选 - 如果未提供则使用默认值)
- **reviewMode**：
  - `full`：完整验证 (默认)
  - `structure`：仅结构合规性
  - `content`：仅内容质量
  - `failure-scenarios`：仅故障场景覆盖范围

## 完成条件

□ 已加载文档并确认类型
□ 已根据模板验证结构合规性
□ 已评估内容质量
□ 已审查故障场景 (对于设计文档)
□ 已记录问题及其严重性
□ 已确定结论并说明理由

## 审查流程

### 阶段 1: 文档类型识别

确认文档类型并确定验证基线：
- 如果提供了模板路径 → 使用指定的模板作为基线
- 如果没有提供模板 → 向用户请求模板路径
- 按类型的默认模板：
  - 设计文档 → `.agents/tasks/technical-design.md`
  - ADR → `.agents/tasks/technical-design.md` 中的 ADR 部分
  - PRD → `.agents/skills/documentation-criteria/SKILL.md` 中的 PRD 部分

### 阶段 2: 结构合规性检查

#### 关卡 0: 结构存在性 (必须在质量审查前通过)
根据模板验证所需元素是否存在。任何项目的关卡 0 失败 → `blocked` (阻塞)。

#### 对于设计文档

| 必要部分 | 检查项 |
|-----------------|------------|
| 概述 | 目的已清晰陈述 |
| 设计摘要 (元数据) | `risk_level` (风险等级)、`constraints` (约束)、`unknowns` (未知项) 已定义 |
| 协议清单 | 范围/非范围/约束已记录 |
| 现有代码库分析 | 包含调查结果 |
| 适用标准 | 列出了显式/隐式分类 |
| 代码检查证据 | 记录了检查过的文件和函数 |
| 验收标准 | 具体、可测试的条件 |
| 架构 | 定义了方法、组件、数据流 |
| 集成点 | 识别了外部依赖 |
| 字段传播图 | 当字段跨越边界时存在 |
| 测试策略 | 概述了测试方法 |
| 风险与缓解措施 | 记录了技术风险 |
| 参考文献 | 引用了来源 |

#### 关卡 1: 质量评估 (仅在关卡 0 通过后)
只有在所有关卡 0 结构检查通过后，才进行阶段 3-5。

#### 对于 ADR

| 必要部分 | 检查项 |
|-----------------|------------|
| 背景 | 用1-2句话描述问题背景 |
| 选项 | 评估了至少3个选项 |
| 比较矩阵 | 量化了权衡取舍 |
| 决策 | 选定的选项及其理由 |
| 决策详情 | 为何现在/为何是这个/已知的未知/终止标准 |
| 实现指南 | 基于原则的指南 |
| 参考文献 | 引用了文档 URL |

#### 对于 PRD

| 必要部分 | 检查项 |
|-----------------|------------|
| 业务需求 | 阐明了用户价值 |
| 成功指标 | KPI 以可衡量格式呈现 |
| 用户故事 | 记录了用例 |
| MoSCoW 优先级 | 定义了必须/应该/可以/不会做 |
| 范围边界 | 分隔了 MVP 和未来阶段 |

### 阶段 3: 内容质量检查

| 检查项 | 验证内容 | 失败条件 |
|------------|---------------------|-------------------|
| 具体性 | 具体，而非模糊 | 没有例子的抽象陈述 |
| 可测试性 | 验收标准可验证 | 无法测试 |
| 一致性 | 无内部矛盾 | 各部分相互矛盾 |
| 完整性 | 所有必要部分都存在且有深度 | 缺少部分 |
| 清晰度 | 语言无歧义 | 可能有多种解释 |
| 理由验证 | 设计决策引用了已识别的标准 | 没有标准参考的无法验证的理由 |
| 代码检查证据 | 检查的文件与设计范围相关 | 关键相关文件在证据中缺失 |

### 阶段 4: 故障场景审查 (仅限设计文档)

识别三类故障场景：

| 类别 | 描述 | 必要覆盖范围 |
|----------|-------------|-------------------|
| 正常使用 | 典型操作期间的故障 | 至少1个场景 |
| 高负载 | 压力下的故障 | 至少1个场景 |
| 外部故障 | 来自依赖项的故障 | 至少1个场景 |

对于每个识别的场景，验证：
- 故障场景已明确记录
- 指定了瓶颈元素
- 定义了缓解策略

### 阶段 5: 技术声明验证

当存在来源时：
- 用当前的最佳实践验证声明
- 检查引用的技术/版本是否为最新
- 标记过时的信息

## 验证清单

### 结构验证
- [ ] 所有必要部分都存在
- [ ] 部分顺序遵循模板
- [ ] 格式一致

### 内容验证
- [ ] 验收标准具体且可测试
- [ ] 技术决策有理有据
- [ ] 风险已识别并有缓解措施
- [ ] 参考文献已引用且有效

### 故障场景验证 (设计文档)
- [ ] 已识别正常使用故障场景
- [ ] 已识别高负载故障场景
- [ ] 已识别外部故障场景
- [ ] 为每个场景指定了瓶颈

### 一致性验证
- [ ] 各部分之间无矛盾
- [ ] 术语使用一致
- [ ] 整个文档范围一致

### 设计文档额外验证
- [ ] 关卡 0 结构存在性检查在质量审查前通过
- [ ] 设计决策的理由根据已识别的标准/模式进行了验证
- [ ] 代码检查证据覆盖了与设计范围相关的文体
- [ ] 当字段跨越组件边界时存在字段传播图

## 输出格式

### 状态确定

**approved (已批准)**:
- 关卡 0: 所有结构存在性检查通过
- 所有必要部分都存在且完整
- 内容具体且可测试
- 故障场景已覆盖 (设计文档)
- 没有高严重性问题

**needs_revision (需要修订)**:
- 关卡 0: 所有结构存在性检查通过
- 某些部分不完整
- 存在内容质量问题
- 故障场景部分覆盖
- 存在中等严重性问题
- 复杂度为中/高，但理由未能证明其必要性 (设计文档)

**blocked (阻塞)**:
- 关卡 0: 任何结构存在性检查失败 或
- 关键部分缺失
- 发现重大矛盾
- 文档类型不明确
- 未经重大重写无法继续

## 审查原则

1.  **模板合规性**
    - 使用文档类型模板作为基线
    - 验证所有必要元素是否存在

2.  **建设性反馈**
    - 提供具体的改进建议
    - 按影响对问题进行优先级排序

3.  **客观性**
    - 根据已记录的标准进行评估
    - 避免主观偏好

4.  **可操作性**
    - 每个问题都应有明确的解决路径
    - 区分必须修复和建议改进

## 上报标准

在以下情况时建议上报：
- 文档与现有的 ADR 矛盾
- 未解决安全隐患
- 范围显著超出原始需求
- 技术声明无法验证

## 要避免的反模式

- 批准缺少必要部分的文档
- 忽略模糊的验收标准
- 忽视故障场景的差距
- 接受没有参考文献的文档
- 提供没有具体解决方案的反馈
